# Процеси та потоки

Перш ніж писати конкурентний код на Python, треба чітко уявляти, що саме виконує операційна система: **процеси** і **потоки**. У цій темі пояснюємо, що це таке, як вони спільно використовують (або не використовують) пам'ять, як процесор виконує багато задач «одночасно» і що обрати для якої роботи.

## Що ви дізнаєтесь

- Як програма на Python перетворюється на запущений процес
- Що таке процес і потік і як вони пов'язані
- Чим конкурентність відрізняється від паралелізму і як їх забезпечує планувальник ОС
- Як відрізнити задачі, обмежені введенням-виведенням (I/O-bound), від задач, обмежених процесором (CPU-bound)
- Що таке GIL, що змінює збірка CPython без GIL і чому це важливо для вибору між потоками й процесами
- Практичні відмінності між процесами та потоками

## Від програми до процесу

Візьмімо крихітну програму у файлі `app.py`:

```python
x = 10
y = 20
z = x + y
```

Процесор не вміє виконувати код Python напряму, він виконує лише **машинний код**. Коли ви запускаєте `python app.py`, відбувається таке:

1. Операційна система (ОС) завантажує в пам'ять інтерпретатор Python (CPython, тобто програму, написану на C і скомпільовану в машинний код) і запускає його.
2. CPython **компілює** ваш код у **байт-код** (bytecode): компактні низькорівневі інструкції для віртуальної машини. Байт-код не є машинним кодом.
3. Цикл виконання CPython читає інструкції байт-коду одну за одною й виконує їх. Тобто процесор виконує машинний код інтерпретатора, а інтерпретатор виконує ваш байт-код.

Байт-код можна побачити за допомогою модуля `dis`:

```python
import dis

dis.dis("z = x + y")
```

Результат (Python 3.14; конкретні інструкції змінюються між версіями):

```text
  0           RESUME                   0

  1           LOAD_NAME                0 (x)
              LOAD_NAME                1 (y)
              BINARY_OP                0 (+)
              STORE_NAME               2 (z)
              LOAD_CONST               0 (None)
              RETURN_VALUE
```

> **Зверніть увагу:** у старіших посібниках пишуть, що CPython «компілює Python у машинний код». Стандартний CPython працює не так: він компілює код у байт-код та інтерпретує його. У Python 3.13+ з'явився експериментальний JIT-компілятор, але він типово вимкнений і цієї базової моделі не змінює.

## Процеси та потоки

**Процес (process) — це екземпляр запущеної програми.** ОС надає кожному процесу:

- власну приватну **пам'ять** (адресний простір), яку інші процеси не можуть напряму читати чи змінювати;
- власні ресурси: відкриті файли, мережеві з'єднання, змінні середовища;
- унікальний номер — **ідентифікатор процесу (PID)**;
- щонайменше один потік.

**Потік (thread) — це одиниця виконання всередині процесу.** Саме потік ОС ставить на ядро процесора. Кожен потік має власний вказівник інструкцій («де я зараз у коді») і власний стек викликів, але всі потоки одного процесу **спільно використовують** його пам'ять: глобальні змінні, об'єкти в купі, відкриті файли.

```text
+------------------- процес (PID 4120) --------------------+
|  спільна пам'ять: глобальні змінні, об'єкти, файли      |
|                                                          |
|   +-------------+   +-------------+   +-------------+    |
|   |  головний   |   |   потік 2   |   |   потік 3   |    |
|   | власний стек|   | власний стек|   | власний стек|    |
|   +-------------+   +-------------+   +-------------+    |
+----------------------------------------------------------+
```

Зручна аналогія: **програма** схожа на клас, а **процеси** — на його екземпляри. Якщо запустити ту саму програму тричі, програма буде одна, а процесів три, кожен зі своєю пам'яттю та PID.

Досі всі ваші програми мали **один процес з одним потоком** — **головним потоком** (main thread). Тому ці два слова часто вживають як синоніми. Загалом:

- програма може запустити один або кілька процесів, а кожен процес може мати один або кілька потоків;
- програма, що використовує кілька процесів, працює в режимі **багатопроцесності** (multiprocessing);
- програма, що використовує кілька потоків в одному процесі, працює в режимі **багатопотоковості** (multithreading).

Python може підказати, де саме виконується ваш код:

```python
import os
import threading

print("Process ID (PID):", os.getpid())
print("Parent PID:", os.getppid())
print("Current thread:", threading.current_thread().name)
print("Threads in this process:", threading.active_count())
```

Результат (PID щоразу інші):

```text
Process ID (PID): 34149
Parent PID: 34144
Current thread: MainThread
Threads in this process: 1
```

Батьківський PID належить програмі, яка запустила Python, зазвичай вашій оболонці (shell).

### Потоки спільно використовують пам'ять, процеси — ні

Це найважливіша практична відмінність. У прикладі нижче і потік, і дочірній процес додають елемент до глобального списку `shared`:

```python
import multiprocessing
import threading

shared = []


def add_item(source):
    shared.append(source)
    print(f"inside the {source}: {shared}")


if __name__ == "__main__":
    t = threading.Thread(target=add_item, args=("thread",))
    t.start()
    t.join()
    print("main after the thread: ", shared)

    p = multiprocessing.Process(target=add_item, args=("process",))
    p.start()
    p.join()
    print("main after the process:", shared)
```

Результат (macOS і Windows, Python 3.14):

```text
inside the thread: ['thread']
main after the thread:  ['thread']
inside the process: ['process']
main after the process: ['thread']
```

- Потік змінив **той самий** список, який бачить головний потік.
- Дочірній процес отримав **власну копію** пам'яті програми. Він змінив свою копію, і батьківський процес цієї зміни не побачив.

> **Зверніть увагу:** що саме дочірній процес бачить *на старті*, залежить від способу запуску (start method). Зі `spawn` (типовий на macOS і Windows) та `forkserver` (типовий на Linux починаючи з Python 3.14) дочірній процес імпортує ваш модуль заново, тому починає з порожнього списку. З `fork` (типовий на Linux до 3.14) дочірній процес стартує з копією пам'яті батька й виводить `['thread', 'process']`. Але в усіх випадках список батьківського процесу не змінюється. Захист `if __name__ == "__main__":` обов'язковий, щоб дочірній процес, повторно імпортуючи модуль, сам не почав запускати процеси.

## Як процесор виконує багато всього «одночасно»

### Одне ядро: по черзі

Одне ядро процесора виконує в кожен момент лише один потік. Щоб багато програм працювали «одночасно», ОС використовує компонент, який називається **планувальник** (scheduler). Він дає кожному готовому потоку короткий **квант часу** (зазвичай кілька мілісекунд), потім призупиняє його, зберігає стан і перемикається на інший потік. Це **перемикання контексту** (context switch). Воно відбувається так часто, що здається, ніби все працює одночасно.

```text
одне ядро:  [A][B][C][A][B][C][A][B] ...   -> час
            задачі чергуються: конкурентність, але не паралелізм
```

### Багато ядер: справді одночасно

Сучасні процесори мають кілька **ядер** (2, 4, 8, 10 і більше). Кожне ядро може виконувати свій потік у той самий момент. Маючи *N* ядер, можна справді паралельно виконувати до *N* потоків (трохи більше на процесорах з одночасною багатопотоковістю, як-от Intel Hyper-Threading).

```text
ядро 1:  [A][A][A][A][A] ...
ядро 2:  [B][B][B][B][B] ...   -> A і B справді працюють паралельно
```

Звідси два пов'язані, але різні поняття:

- **Конкурентність** (concurrency): кілька задач *перебувають у процесі виконання* протягом того самого проміжку часу. Вони можуть чергуватися на одному ядрі.
- **Паралелізм** (parallelism): кілька задач *виконуються в ту саму мить* на різних ядрах.

Python може повідомити, скільки логічних процесорів йому доступно:

```python
import os

print(os.cpu_count())          # логічні процесори машини, напр. 10
print(os.process_cpu_count())  # процесори, доступні цьому процесу (Python 3.13+), напр. 10
```

## Задачі, обмежені процесором і введенням-виведенням

Чи допоможе конкурентність, залежить від того, на що ваш код витрачає час.

- Задачі, **обмежені введенням-виведенням** (I/O-bound), здебільшого **чекають**: на відповідь мережі, запит до бази даних, читання чи запис диска, дію користувача. Під час очікування процесор простоює. Приклади: завантаження вебсторінок, виклики API, запити до БД, читання багатьох файлів.
- Задачі, **обмежені процесором** (CPU-bound), здебільшого **обчислюють**. Процесор зайнятий увесь час. Приклади: множення матриць, пошук простих чисел, зміна розміру зображень, стиснення чи кодування відео, хешування паролів.

```text
I/O-bound:  [cpu]....очікування....[cpu]....очікування....[cpu]
CPU-bound:  [cpu][cpu][cpu][cpu][cpu][cpu][cpu][cpu][cpu]
```

Для I/O-bound задач секрет у тому, щоб **робити щось корисне під час очікування**: розпочати наступне завантаження, поки перше чекає на відповідь. Потоки (або `asyncio`) роблять це дешево. У CPU-bound задачах немає очікування, яке можна перекрити. Єдиний спосіб пришвидшитися — задіяти **більше ядер одночасно**.

## GIL: чому потоки Python не працюють паралельно

Стандартний CPython має **глобальне блокування інтерпретатора** (Global Interpreter Lock, GIL). Це блокування всередині інтерпретатора, яке дозволяє **лише одному потоку процесу водночас виконувати байт-код Python**. Воно підтримує цілісність внутрішніх структур CPython (наприклад, лічильників посилань) без дрібних блокувань усюди.

Наслідки:

- **CPU-bound код на Python не пришвидшується від потоків.** Два потоки, що обчислюють, по черзі захоплюють GIL, тож разом використовують приблизно одне ядро.
- **I/O-bound код від потоків пришвидшується.** Потік звільняє GIL, поки чекає на введення-виведення або спить (`time.sleep()`, читання із сокета, читання файлу), тож тим часом можуть працювати інші потоки.
- Багато розширень на C звільняють GIL під час важкої роботи (наприклад, `hashlib` для великих даних, `zlib`, операції NumPy). Такий код потоки теж можуть пришвидшити.
- Інтерпретатор періодично просить потік, що працює, віддати GIL: типово кожні 5 мс (`sys.getswitchinterval()`). Тож потоки все одно чергуються справедливо.
- **Кожен процес має власний інтерпретатор і власний GIL.** Тому багатопроцесність дає справжній паралелізм для CPU-bound коду на Python.

### CPython без GIL (PEP 703)

Починаючи з **Python 3.13** існує необов'язкова **збірка CPython без GIL** (free-threaded build), яку часто встановлюють як `python3.13t` / `python3.14t`. У 3.13 вона була експериментальною. У **3.14** її офіційно підтримують (PEP 779), але це й далі окрема, необов'язкова збірка, а не типова. У ній потоки можуть виконувати код Python паралельно на кількох ядрах. Однопотоковий код працює трохи повільніше, а деякі розширення на C ще несумісні (імпорт такого розширення може знову ввімкнути GIL).

Перевірити, яку збірку ви запустили, можна так:

```python
import sys
import sysconfig

print("Python:", sys.version.split()[0])
print("Free-threaded build:", bool(sysconfig.get_config_var("Py_GIL_DISABLED")))
print("GIL enabled right now:", sys._is_gil_enabled())
```

Результат (стандартна збірка 3.14 з python.org):

```text
Python: 3.14.0
Free-threaded build: False
GIL enabled right now: True
```

`sys._is_gil_enabled()` існує з Python 3.13. Підкреслення на початку означає, що функція специфічна для CPython.

### Практичне правило

| Тип роботи | Стандартний CPython (з GIL) | CPython без GIL |
|---|---|---|
| I/O-bound | потоки (або `asyncio`) | потоки (або `asyncio`) |
| CPU-bound, чистий Python | процеси | потоки або процеси |
| CPU-bound у бібліотеці на C, що звільняє GIL | потоки часто допомагають | потоки |

## Основні відмінності між процесами та потоками

| Критерій | Процес | Потік |
|---|---|---|
| Пам'ять | Власний адресний простір, типово не спільний | Спільна пам'ять свого процесу |
| Витрати пам'яті | Великі: цілий інтерпретатор на процес | Малі: здебільшого власний стек |
| Час запуску | Повільний (мілісекунди) | Швидкий (десятки мікросекунд) |
| Обмін даними | Канали (pipes), черги, спільна пам'ять; дані копіюються (серіалізуються через pickle) | Пряме читання й запис тих самих об'єктів; потрібні блокування |
| Ізоляція | Аварія одного процесу не зачіпає інших | Аварія в нативному коді вбиває весь процес |
| Зупинка ззовні | Можна завершити примусово (`terminate()`, `kill()`) | Не можна «вбити»; зупинка лише за домовленістю |
| Паралельний код Python (з GIL) | Так, кожен процес має свій GIL | Ні, лише один потік водночас |
| Найкраще підходить для | CPU-bound задач | I/O-bound задач |

Різницю в часі запуску легко виміряти:

```python
import multiprocessing
import threading
import time


def do_nothing():
    pass


def measure(worker_class, count=20):
    start = time.perf_counter()
    workers = [worker_class(target=do_nothing) for _ in range(count)]
    for w in workers:
        w.start()
    for w in workers:
        w.join()
    return time.perf_counter() - start


if __name__ == "__main__":
    print(f"20 threads:   {measure(threading.Thread):.4f} s")
    print(f"20 processes: {measure(multiprocessing.Process):.4f} s")
```

Результат (час залежить від машини й запуску):

```text
20 threads:   0.0007 s
20 processes: 0.1535 s
```

Запуск процесу через `spawn` означає старт нового інтерпретатора й повторний імпорт вашого модуля. Це приблизно в сто разів дорожче, ніж запуск потоку. Тому і потоки, і процеси зазвичай використовують повторно через **пули** (про них далі в цьому розділі).

## Типові помилки

- **Очікувати, що потоки пришвидшать CPU-bound код на Python.** З GIL байт-код виконує лише один потік водночас. Використовуйте процеси або збірку без GIL.
- **Очікувати, що процеси спільно використовують глобальні змінні.** Дочірній процес працює з власною копією. Передавайте дані явно: аргументами, через черги, через результати пулу.
- **Забути `if __name__ == "__main__":`** навколо коду, що запускає процеси. Зі `spawn` і `forkserver` дочірній процес повторно імпортує ваш модуль, і незахищений код спробував би знову запускати процеси (Python зупиняє це винятком `RuntimeError`).
- **Плутати конкурентність із паралелізмом.** Потоки з GIL дають конкурентність (перекривання очікувань), а не паралельні обчислення.
- **Запускати набагато більше процесів, ніж є ядер,** для CPU-bound роботи. Зайві процеси лише додають витрат на перемикання та пам'ять. Беріть приблизно `os.process_cpu_count()` робочих процесів.
- **Вважати, що способи запуску поводяться однаково всюди.** Код, який «працював» із `fork` на Linux, може зламатися зі `spawn` на macOS і Windows. Пишіть код, що працює зі `spawn`.

## Підсумок

- Процес — це запущений екземпляр програми з власною пам'яттю та PID. Потік — це одиниця виконання всередині процесу.
- Кожен процес має щонайменше один потік (головний). Потоки одного процесу спільно використовують його пам'ять, а процеси типово пам'ять не ділять.
- CPython компілює код у байт-код та інтерпретує його.
- Планувальник ОС перемикає потоки на кожному ядрі кожні кілька мілісекунд (конкурентність). Кілька ядер виконують потоки справді одночасно (паралелізм).
- I/O-bound задачі здебільшого чекають, CPU-bound задачі здебільшого обчислюють.
- GIL дозволяє лише одному потоку водночас виконувати байт-код Python, тому в стандартному CPython використовуйте потоки для I/O-bound задач, а процеси для CPU-bound.
- CPython без GIL (необов'язкова збірка з 3.13, офіційно підтримувана з 3.14) дозволяє потокам виконувати код Python паралельно.
- Процеси важчі й повільніше запускаються, зате ізольовані. Потоки дешеві, але все ділять між собою, тому потребують синхронізації.

## Практика

### Вправа 1: I/O-bound чи CPU-bound?

Визначте тип кожної задачі та скажіть, чим би ви пришвидшили її в стандартному CPython: потоками чи процесами.

### Вправа 2: Передбачте результат

```python
import multiprocessing
import threading

settings = {"mode": "default"}


def change_mode(new_mode):
    settings["mode"] = new_mode


if __name__ == "__main__":
    t = threading.Thread(target=change_mode, args=("thread",))
    t.start()
    t.join()
    print(settings["mode"])

    p = multiprocessing.Process(target=change_mode, args=("process",))
    p.start()
    p.join()
    print(settings["mode"])
```

### Вправа 3

```python
import multiprocessing
import os
import threading

seen_pids = set()


def record_pid():
    seen_pids.add(os.getpid())


def check_parent(parent_pid):
    print("child PID differs from parent PID:", os.getpid() != parent_pid)
    print("child's parent is our main process:", os.getppid() == parent_pid)


if __name__ == "__main__":
    threads = [threading.Thread(target=record_pid) for _ in range(3)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print("distinct PIDs seen by threads:", len(seen_pids))
    print("equal to the main PID:", seen_pids == {os.getpid()})

    p = multiprocessing.Process(target=check_parent, args=(os.getpid(),))
    p.start()
    p.join()
```

Результат:

```text
distinct PIDs seen by threads: 1
equal to the main PID: True
child PID differs from parent PID: True
child's parent is our main process: True
```

Усі потоки живуть усередині головного процесу, тому бачать один PID. Дочірній процес — окремий процес із власним PID, а його батько — процес, який його запустив.

### Вправа 4

```python
import threading
import time


def io_task():
    time.sleep(0.2)  # очікування: GIL звільнено


def cpu_task():
    total = 0
    for i in range(5_000_000):  # обчислення: GIL захоплено
        total += i


def sequential(task, times=4):
    start = time.perf_counter()
    for _ in range(times):
        task()
    return time.perf_counter() - start


def threaded(task, times=4):
    start = time.perf_counter()
    threads = [threading.Thread(target=task) for _ in range(times)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - start


if __name__ == "__main__":
    for task in (io_task, cpu_task):
        print(f"{task.__name__}: sequential {sequential(task):.2f} s, "
              f"4 threads {threaded(task):.2f} s")
```

Результат (час різниться; стандартний CPython із GIL):

```text
io_task: sequential 0.81 s, 4 threads 0.21 s
cpu_task: sequential 0.30 s, 4 threads 0.28 s
```

Чотири очікування перекриваються, тому потокова I/O-версія триває приблизно стільки ж, скільки одне очікування. CPU-bound версія нічого не виграє: потоки по черзі захоплюють GIL і разом усе одно використовують приблизно одне ядро. У збірці без GIL час потокової CPU-bound версії теж зменшився б.
