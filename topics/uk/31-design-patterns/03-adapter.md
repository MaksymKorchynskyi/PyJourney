# Адаптер

**Адаптер** (Adapter), також відомий як **Обгортка** (Wrapper), — це структурний патерн проєктування, що дає змогу об'єктам із несумісними інтерфейсами працювати разом. Адаптер стоїть між вашим кодом і класом, який ви не можете або не повинні змінювати, і перекладає виклики та дані з однієї форми в іншу. Саме по нього ви тягнетеся щоразу, коли стороння бібліотека, застарілий модуль чи зовнішній API «майже» підходять.

## Що ви дізнаєтесь

- Як розпізнати невідповідність інтерфейсів і чому змінити іншу сторону часто неможливо
- Ролі патерна: Клієнт, Клієнтський інтерфейс, Сервіс і Адаптер
- Адаптери об'єктів (композиція) та адаптери класів (успадкування) на Python
- Практичний адаптер XML → JSON для сторонньої аналітичної бібліотеки
- Адаптери, які вже є в стандартній бібліотеці: `functools.cmp_to_key` та `io.TextIOWrapper`
- Пастки: витік винятків, бізнес-логіка в адаптері та прозоре пересилання через `__getattr__`

## Суть патерна

Адаптер перетворює інтерфейс одного об'єкта на інший інтерфейс, якого очікує клієнт. Клієнт і далі спілкується зі «своїм» інтерфейсом. Адаптер приймає ці виклики, за потреби перетворює аргументи й результати та передає роботу обгорнутому об'єкту, який навіть не знає, що його адаптують.

## Проблема

Уявіть застосунок для моніторингу фондового ринку. Він завантажує котирування з кількох бірж у форматі **XML** і будує графіки. Ви вирішуєте підключити розумну сторонню аналітичну бібліотеку й натрапляєте на заковику: бібліотека приймає дані лише в **JSON**.

```python
import json


class AnalyticsLibrary:
    """Сторонній код: очікує JSON, і змінити його ми не можемо."""

    def analyze(self, payload: str) -> str:
        quotes = json.loads(payload)
        return f"{len(quotes)} quotes analysed"


xml_feed = '<quotes><quote symbol="ACME" price="12.50"/></quotes>'
try:
    AnalyticsLibrary().analyze(xml_feed)
except json.JSONDecodeError as error:
    print("JSONDecodeError:", error)
```

Результат:

```text
JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

Які є варіанти?

- **Змінити бібліотеку, щоб вона приймала XML.** Її вихідного коду у вас може взагалі не бути. А навіть якщо він є, ваш патч зникне з наступним оновленням і може зламати інший код, що залежить від бібліотеки.
- **Переробити весь застосунок на JSON.** Це означає переписати робочий код усюди заради одного споживача.
- **Конвертувати дані в кожному місці виклику.** Тоді той самий код перетворення розповзеться по всьому застосунку.

Жоден варіант не вабить. Потрібен один невеликий об'єкт, що виконує переклад в одному місці.

## Рішення

Створіть **адаптер** — спеціальний об'єкт, що перетворює інтерфейс одного об'єкта так, щоб інший об'єкт міг його зрозуміти. Адаптер обгортає один з об'єктів і приховує складність перетворення. Обгорнутий об'єкт про адаптер не знає.

Адаптер може перетворювати формати даних (XML на JSON, метри на фути, гривні в `Decimal` на цілі копійки), а може й узгоджувати різні назви методів і послідовності викликів:

1. Адаптер надає інтерфейс, сумісний з одним з наявних об'єктів (клієнтом).
2. Клієнт викликає методи адаптера через цей інтерфейс, наче це звичайний співрозмовник.
3. Отримавши виклик, адаптер передає запит другому об'єкту (сервісу) у тому форматі й порядку, якого той очікує.

Іноді можна навіть створити **двобічний адаптер**, що перетворює виклики в обох напрямках.

Для застосунку з котируваннями ви пишете адаптер XML → JSON для кожного класу аналітичної бібліотеки, з яким працює ваш код, і дозволяєте застосунку спілкуватися з бібліотекою лише через ці адаптери.

## Аналогія з життя

Під час першої поїздки зі США до Європи з'ясовується, що вилка зарядного пристрою ноутбука не пасує до розетки: стандарти різні. Ви не перебудовуєте проводку в готелі й не відрізаєте вилку. Ви купуєте маленький перехідник, у якого з одного боку американське гніздо, а з другого — європейська вилка. Ні ноутбук, ні розетка про нього не знають, і кожен зберігає свій «інтерфейс».

## Структура

Є два класичні варіанти.

**Адаптер об'єктів** використовує композицію: адаптер реалізує клієнтський інтерфейс і *містить* об'єкт сервісу. Він працює в будь-якій мові й зазвичай є вибором за замовчуванням у Python.

```text
+----------+        +---------------------------+
|  Client  |------->|       <<interface>>       |
+----------+  uses  |      ClientInterface      |
                    |---------------------------|
                    | + method(data)            |
                    +---------------------------+
                                  ^
                                  | implements
                    +---------------------------+         +-----------------------------+
                    |          Adapter          |  wraps  |           Service           |
                    |---------------------------|-------->|-----------------------------|
                    | - adaptee: Service        |         | + service_method(special)   |
                    | + method(data)            |         +-----------------------------+
                    +---------------------------+

method(data):
    special = convert_to_service_format(data)
    return self.adaptee.service_method(special)
```

**Адаптер класів** використовує успадкування: адаптер успадковує сервіс (а якщо цільовий інтерфейс — клас, то і його), тож нічого не обгортає. Для цього потрібне множинне успадкування, яке Python підтримує.

```text
+---------------------------+       +-----------------------------+
|     ClientInterface       |       |           Service           |
|---------------------------|       |-----------------------------|
| + method(data)            |       | + service_method(special)   |
+---------------------------+       +-----------------------------+
              ^                                   ^
              +-----------------+-----------------+
                                | inherits from both
                  +---------------------------+
                  |          Adapter          |
                  |---------------------------|
                  | + method(data):           |
                  |     self.service_method(  |
                  |         convert(data))    |
                  +---------------------------+
```

1. **Клієнт** (Client) містить наявну бізнес-логіку.
2. **Клієнтський інтерфейс** (Client Interface) описує протокол, якого мають дотримуватися інші класи, щоб співпрацювати з клієнтом.
3. **Сервіс** (Service) — корисний клас (часто сторонній або застарілий) з несумісним інтерфейсом.
4. **Адаптер** (Adapter) реалізує клієнтський інтерфейс і перекладає кожен виклик у виклики сервісу.
5. Доки клієнт залежить лише від клієнтського інтерфейсу, можна додавати нові адаптери або замінювати наявний, коли змінюється сервіс, не чіпаючи клієнта.

## Реалізація на Python

Класичний приклад: у круглий отвір входять круглі кілки, а нам треба перевірити, чи пролізуть *квадратні*. Квадратний кілок має `width`, а не `radius`, тож отвір не може працювати з ним напряму. Адаптер прикидається круглим кілком, радіус якого дорівнює радіусу найменшого кола навколо квадрата, тобто половині його діагоналі: `width * sqrt(2) / 2`.

```python
import math
from typing import Protocol


class RoundPegLike(Protocol):
    """Клієнтський інтерфейс: будь-що з радіусом."""

    @property
    def radius(self) -> float: ...


class RoundHole:
    """Клієнт."""

    def __init__(self, radius: float) -> None:
        self.radius = radius

    def fits(self, peg: RoundPegLike) -> bool:
        return self.radius >= peg.radius


class RoundPeg:
    def __init__(self, radius: float) -> None:
        self.radius = radius


class SquarePeg:
    """Сервіс: корисний, але його інтерфейс не підходить."""

    def __init__(self, width: float) -> None:
        self.width = width


class SquarePegAdapter:
    """Адаптер об'єктів: обгортає SquarePeg і виглядає як круглий кілок."""

    def __init__(self, peg: SquarePeg) -> None:
        self._peg = peg

    @property
    def radius(self) -> float:
        # Радіус найменшого кола, що вміщує квадрат: половина діагоналі.
        return self._peg.width * math.sqrt(2) / 2


hole = RoundHole(5)
print("round peg r=5:", hole.fits(RoundPeg(5)))

small, large = SquarePeg(5), SquarePeg(10)
try:
    hole.fits(small)
except AttributeError as error:
    print("square peg directly:", error)

for peg in (small, large):
    adapter = SquarePegAdapter(peg)
    print(f"square peg w={peg.width} (r={adapter.radius:.2f}):", hole.fits(adapter))
```

Результат:

```text
round peg r=5: True
square peg directly: 'SquarePeg' object has no attribute 'radius'
square peg w=5 (r=3.54): True
square peg w=10 (r=7.07): False
```

`Protocol` описує клієнтський інтерфейс структурно: ні `RoundPeg`, ні `SquarePegAdapter` не успадковують його, проте перевіряльник типів приймає обидва, бо в обох є `radius`. Ні `RoundHole`, ні `SquarePeg` не змінилися.

### Адаптер класів

У Python адаптер класів просто успадковує сервіс і додає методи, яких очікує клієнт:

```python
# Продовження попереднього прикладу
class SquarePegClassAdapter(SquarePeg):
    """Адаптер класів: це SquarePeg, який водночас поводиться як круглий кілок."""

    @property
    def radius(self) -> float:
        return self.width * math.sqrt(2) / 2


peg = SquarePegClassAdapter(7)
print(f"w={peg.width}, r={peg.radius:.2f}, fits: {hole.fits(peg)}")
print(isinstance(peg, SquarePeg))
```

Результат:

```text
w=7, r=4.95, fits: True
True
```

Якщо цільовий інтерфейс сам є конкретним класом чи `ABC`, адаптер класів успадковує обидва: `class Adapter(Target, Service)`. Порівняймо два варіанти:

| | Адаптер об'єктів | Адаптер класів |
|---|---|---|
| Механізм | Композиція: містить об'єкт сервісу | Успадкування від класу сервісу |
| Чи може адаптувати вже наявний об'єкт | Так, можна обгорнути будь-який отриманий екземпляр | Ні, адаптер доводиться створювати *замість* сервісу |
| Працює з підкласами сервісу | Так | Лише з тим класом, від якого успадковує |
| Може змінити поведінку сервісу | Ні (лише обгорнути) | Так |
| Відкриває клієнтові методи сервісу | Лише ті, які ви переслали | Усі, а це може розкрити зайві деталі |

Віддавайте перевагу адаптеру об'єктів, якщо немає конкретної причини для успадкування.

### Адаптери в стандартній бібліотеці

Сам Python постачається з адаптерами. `functools.cmp_to_key()` адаптує функцію порівняння старого стилю (повертає від'ємне число, нуль чи додатне) до інтерфейсу `key=`, якого очікує `sorted()`. `io.TextIOWrapper` адаптує двійковий потік до інтерфейсу текстового файлу:

```python
import io
from functools import cmp_to_key


def compare_versions(a: str, b: str) -> int:
    left = [int(part) for part in a.split(".")]
    right = [int(part) for part in b.split(".")]
    return (left > right) - (left < right)


versions = ["1.10.0", "1.2.3", "1.9.12"]
print(sorted(versions))
print(sorted(versions, key=cmp_to_key(compare_versions)))

raw = io.BytesIO("Київ\nЛьвів\n".encode("utf-8"))  # лише байти
text = io.TextIOWrapper(raw, encoding="utf-8")      # адаптер: тепер читаємо str
print([line.strip() for line in text])
```

Результат:

```text
['1.10.0', '1.2.3', '1.9.12']
['1.2.3', '1.9.12', '1.10.0']
['Київ', 'Львів']
```

## Практичний приклад: XML-стрічка для JSON-бібліотеки аналітики

Повернімося до застосунку з котируваннями з розділу *Проблема*. Наша панель очікує об'єкт із методом `analyze_xml()`. Стороння бібліотека пропонує `analyze()`, що приймає JSON. Адаптер говорить з нашим кодом мовою XML, а з бібліотекою — мовою JSON:

```python
import json
import xml.etree.ElementTree as ET
from typing import Protocol


class AnalyticsLibrary:
    """Сторонній сервіс: очікує JSON-масив об'єктів {"symbol", "price"}."""

    def analyze(self, payload: str) -> str:
        quotes = json.loads(payload)
        top = max(quotes, key=lambda quote: quote["price"])
        average = sum(quote["price"] for quote in quotes) / len(quotes)
        return f"{len(quotes)} quotes, average {average:.2f}, top {top['symbol']} at {top['price']:.2f}"


class StockAnalyzer(Protocol):
    """Клієнтський інтерфейс: те, чого очікує наша панель."""

    def analyze_xml(self, xml_feed: str) -> str: ...


class XmlToJsonAnalyticsAdapter:
    """Адаптер: XML назовні, JSON усередині."""

    def __init__(self, library: AnalyticsLibrary) -> None:
        self._library = library

    def analyze_xml(self, xml_feed: str) -> str:
        root = ET.fromstring(xml_feed)
        quotes = [
            {"symbol": node.get("symbol"), "price": float(node.get("price", "nan"))}
            for node in root.iter("quote")
        ]
        if not quotes:
            raise ValueError("feed contains no quotes")
        return self._library.analyze(json.dumps(quotes))


class Dashboard:
    """Клієнт: нічого не знає ні про JSON, ні про аналітичну бібліотеку."""

    def __init__(self, analyzer: StockAnalyzer) -> None:
        self.analyzer = analyzer

    def refresh(self, xml_feed: str) -> None:
        print("Dashboard:", self.analyzer.analyze_xml(xml_feed))


feed = """
<quotes source="exchange-a">
    <quote symbol="ACME" price="12.50"/>
    <quote symbol="GLOBX" price="98.10"/>
    <quote symbol="INITECH" price="45.00"/>
</quotes>
"""

dashboard = Dashboard(XmlToJsonAnalyticsAdapter(AnalyticsLibrary()))
dashboard.refresh(feed)

try:
    dashboard.refresh("<quotes/>")
except ValueError as error:
    print("Error:", error)
```

Результат:

```text
Dashboard: 3 quotes, average 51.87, top GLOBX at 98.10
Error: feed contains no quotes
```

Адаптер займається лише перекладом і тими перевірками, без яких переклад неможливий (порожню стрічку не перетворити на змістовний запит). Якщо постачальник аналітики змінить API або ви перейдете до іншого постачальника, ви напишете новий адаптер. `Dashboard` залишиться як є.

> **Зверніть увагу:** `xml.etree.ElementTree` не захищений від зловмисно сформованого XML. Для даних із ненадійних джерел використовуйте сторонній пакет `defusedxml` з тим самим API.

## Коли застосовувати

- **Ви хочете використати наявний клас, але його інтерфейс не відповідає решті коду.** Адаптер стає шаром перекладу між вашим кодом і застарілим класом, стороннім класом чи будь-яким класом із незручним інтерфейсом.
- **Ви хочете повторно використати кілька наявних підкласів, яким бракує спільної функціональності, а додати її до їхнього суперкласу неможливо.** Замість того щоб наслідувати кожен підклас і дублювати відсутній код, помістіть цей код в один адаптер і обгортайте ним об'єкти. Для цього обгорнуті класи мусять мати спільний інтерфейс, і поле адаптера має бути типізоване саме ним. (Таке застосування дуже близьке до патерна Декоратор.)
- **Ви хочете ізолювати свій код від залежності, яка може змінитися.** Якщо ви спілкуєтеся з бібліотекою лише через власний інтерфейс і адаптер, зміна постачальника зачепить один-єдиний клас.

## Кроки реалізації

1. Переконайтеся, що маєте щонайменше два класи з несумісними інтерфейсами: корисний клас-*сервіс*, який не можна змінити (сторонній, застарілий або з безліччю залежних від нього місць), і один чи кілька класів-*клієнтів*, яким він став би в пригоді.
2. Оголосіть клієнтський інтерфейс: опишіть, як клієнти хочуть спілкуватися із сервісом. У Python для цього ідеально підходить `typing.Protocol`, бо наявні класи задовольняють його без успадкування.
3. Створіть клас адаптера, що відповідає клієнтському інтерфейсу. Поки що залиште методи порожніми.
4. Додайте до адаптера поле, що зберігає об'єкт сервісу. Зазвичай його передають у `__init__`. Іноді зручніше передавати його з кожним викликом.
5. Реалізуйте методи клієнтського інтерфейсу один за одним. Кожен має делегувати справжню роботу сервісу й займатися лише перетворенням інтерфейсів і форматів даних, включно з перетворенням результатів і винятків у зворотному напрямку.
6. Нехай клієнти використовують адаптер лише через клієнтський інтерфейс. Тоді адаптери можна змінювати чи розширювати, не чіпаючи клієнтського коду.

## Переваги та недоліки

| Переваги | Недоліки |
|---|---|
| *Принцип єдиного обов'язку*: код перетворення відокремлено від бізнес-логіки. | Більше класів та інтерфейсів, тож загальна складність зростає. |
| *Принцип відкритості/закритості*: нові адаптери додаються без змін у клієнтському коді. | Іноді простіше змінити клас сервісу під решту коду, якщо він ваш. |
| Дає змогу використовувати сторонній і застарілий код без його модифікації. | Зайвий рівень викликів: трохи більше непрямості під час налагодження. |
| Ізолює ваш код від змін в API сервісу. | Недбалий адаптер може «протікати» типами чи винятками сервісу в клієнт. |

## Зв'язки з іншими патернами

- **Міст** зазвичай проєктують заздалегідь, щоб частини застосунку могли розвиватися незалежно. **Адаптер** зазвичай застосовують до наявного застосунку, щоб змусити несумісні класи працювати разом.
- **Адаптер** надає *інший* інтерфейс до наявного об'єкта. **Декоратор** зберігає інтерфейс або розширює його й підтримує рекурсивну композицію (декоратори, що обгортають декоратори), на яку адаптери не здатні.
- З **Адаптером** ви звертаєтеся до наявного об'єкта через інший інтерфейс. Із **Замісником** інтерфейс лишається тим самим. З **Декоратором** ви звертаєтеся до об'єкта через розширений інтерфейс.
- **Фасад** визначає новий, простіший інтерфейс для цілої підсистеми. **Адаптер** робить придатним до використання наявний інтерфейс і зазвичай обгортає один об'єкт.
- **Міст**, **Стан**, **Стратегія** й до певної міри **Адаптер** мають дуже схожу структуру: усі вони делегують роботу іншому об'єкту через композицію. Проте розв'язують вони різні задачі, і назва патерна підказує іншим розробникам, *яку саме* задачу розв'язуєте ви.

## Типові помилки

- **Бізнес-логіка в адаптері.** Адаптер, що заодно нараховує знижки чи вирішує, кому що показувати, вже не адаптер, а цю логіку потім важко знайти. Обмежтеся перекладом.
- **Витік деталей сервісу.** Якщо адаптер повертає власні об'єкти бібліотеки або випускає назовні її винятки, клієнт однаково прив'язаний до бібліотеки. Перетворюйте результати на власні типи, а чужі винятки обгортайте у свої.
- **Пересилання «всього іншого» через `__getattr__`.** Це зручно, але приховує, які методи адаптер насправді підтримує, заважає перевіряльникам типів і **не** працює для спеціальних методів, бо Python шукає їх у класі, а не в екземплярі:

  ```python
  class ListAdapter:
      def __init__(self, items: list[int]) -> None:
          self._items = items

      def __getattr__(self, name: str):
          return getattr(self._items, name)  # пересилає лише звичайні атрибути


  adapter = ListAdapter([3, 1, 2])
  print(adapter.count(1))
  try:
      len(adapter)
  except TypeError as error:
      print("TypeError:", error)
  ```

  Результат:

  ```text
  1
  TypeError: object of type 'ListAdapter' has no len()
  ```

- **Втрата точності під час перетворення.** Конвертація грошей через `float` або округлення не в тому місці дають помилки на копійку. Використовуйте `Decimal` і перетворюйте явно (див. вправу 2).
- **Адаптування власного коду.** Якщо обидві сторони під вашим контролем, зазвичай краще виправити сам інтерфейс, ніж додавати постійний шар перекладу.
- **Адаптер класів там, де ви отримуєте готові об'єкти.** Адаптер класів не може обгорнути вже наявний екземпляр. Використовуйте адаптер об'єктів.

## Підсумок

- Адаптер дає клієнтові змогу працювати із сервісом, чий інтерфейс не підходить, завдяки об'єкту-перекладачу між ними.
- Клієнт залежить лише від власного інтерфейсу. Адаптер реалізує його й делегує роботу обгорнутому сервісу.
- Адаптер об'єктів (композиція) — вибір за замовчуванням у Python. Адаптер класів (успадкування) може змінювати поведінку сервісу, але не здатен обгорнути наявні екземпляри.
- `typing.Protocol` — природний спосіб описати клієнтський інтерфейс, нікого не змушуючи від нього успадковуватися.
- У стандартній бібліотеці повно адаптерів: `functools.cmp_to_key`, `io.TextIOWrapper` та інші.
- Тримайте адаптери тонкими: перетворюйте аргументи, результати й винятки — і більше нічого.

## Практика

### Вправа 1: Датчик у Фаренгейтах

Клас застарілого драйвера `FahrenheitSensor` має метод `read_fahrenheit() -> float`. Ваш код термостата працює з протоколом `TemperatureSensor`, у якому є `celsius() -> float`, і виводить `"Room: 21.5 °C"`. Напишіть `FahrenheitToCelsiusAdapter` і покажіть його роботу з датчиками, що показують `98.6` і `70.7` °F. Округлюйте до одного знака після коми.

### Вправа 2: Платіжний шлюз

Ваш магазин очікує шлюз із методом `pay(amount: Decimal, order_id: str) -> PaymentResult`, де `PaymentResult` — dataclass з полями `ok: bool` і `reference: str`. SDK платіжного провайдера, який змінити не можна, виглядає так:

```python
class LegacyPayClient:
    """Сторонній SDK: суми — цілі числа в дрібних одиницях (копійках)."""

    LIMIT = 1_000_000  # 10 000,00 грн

    def make_charge(self, cents: int, currency: str, meta: dict[str, str]) -> dict[str, str]:
        if cents > self.LIMIT:
            return {"status": "declined", "id": ""}
        return {"status": "succeeded", "id": f"ch_{meta['order']}_{cents}"}
```

Напишіть `LegacyPayAdapter`, що перетворює гривні в `Decimal` на цілі копійки без похибок рухомої коми, завжди надсилає `"UAH"` і перетворює повернений словник на `PaymentResult`. Перевірте його на `Decimal("19.99")` і `Decimal("15000")`.

### Вправа 3: Власний `cmp_to_key`

Реалізуйте `my_cmp_to_key(cmp)`, що адаптує функцію порівняння до інтерфейсу `key=`. Вона має повертати клас, екземпляри якого обгортають значення й реалізують `__lt__` (цього досить для `sorted()`) через виклик `cmp`. Перевірте, що вона сортує `["1.10.0", "1.2.3", "1.9.12", "1.2.10"]` так само, як `functools.cmp_to_key`.

## Розв'язки

### Вправа 1

```python
from typing import Protocol


class TemperatureSensor(Protocol):
    def celsius(self) -> float: ...


class FahrenheitSensor:
    """Застарілий драйвер: змінити не можна."""

    def __init__(self, value: float) -> None:
        self._value = value

    def read_fahrenheit(self) -> float:
        return self._value


class FahrenheitToCelsiusAdapter:
    def __init__(self, sensor: FahrenheitSensor) -> None:
        self._sensor = sensor

    def celsius(self) -> float:
        return round((self._sensor.read_fahrenheit() - 32) * 5 / 9, 1)


def show(sensor: TemperatureSensor) -> None:
    print(f"Room: {sensor.celsius()} °C")


for reading in (98.6, 70.7):
    show(FahrenheitToCelsiusAdapter(FahrenheitSensor(reading)))
```

Результат:

```text
Room: 37.0 °C
Room: 21.5 °C
```

### Вправа 2

```python
from dataclasses import dataclass
from decimal import ROUND_HALF_UP, Decimal
from typing import Protocol


@dataclass(frozen=True)
class PaymentResult:
    ok: bool
    reference: str


class PaymentGateway(Protocol):
    def pay(self, amount: Decimal, order_id: str) -> PaymentResult: ...


class LegacyPayClient:
    """Сторонній SDK: суми — цілі числа в дрібних одиницях (копійках)."""

    LIMIT = 1_000_000  # 10 000,00 грн

    def make_charge(self, cents: int, currency: str, meta: dict[str, str]) -> dict[str, str]:
        if cents > self.LIMIT:
            return {"status": "declined", "id": ""}
        return {"status": "succeeded", "id": f"ch_{meta['order']}_{cents}"}


class LegacyPayAdapter:
    def __init__(self, client: LegacyPayClient) -> None:
        self._client = client

    def pay(self, amount: Decimal, order_id: str) -> PaymentResult:
        kopecks = int((amount * 100).quantize(Decimal("1"), rounding=ROUND_HALF_UP))
        response = self._client.make_charge(kopecks, "UAH", {"order": order_id})
        return PaymentResult(ok=response["status"] == "succeeded", reference=response["id"])


def checkout(gateway: PaymentGateway, amount: Decimal, order_id: str) -> None:
    result = gateway.pay(amount, order_id)
    print(f"{order_id}: {amount} UAH ->", result)


gateway = LegacyPayAdapter(LegacyPayClient())
checkout(gateway, Decimal("19.99"), "A-17")
checkout(gateway, Decimal("15000"), "A-18")
print(int(19.99 * 100), "<- what float would give")
```

Результат:

```text
A-17: 19.99 UAH -> PaymentResult(ok=True, reference='ch_A-17_1999')
A-18: 15000 UAH -> PaymentResult(ok=False, reference='')
1998 <- what float would give
```

Останній рядок пояснює, чому перетворення виконано через `Decimal`: у `float` вираз `19.99 * 100` дорівнює `1998.9999999999998`, а `int()` відкидає дробову частину й дає `1998` — на копійку менше. `Decimal` зберігає точне значення, а `quantize()` округлює його явно.

### Вправа 3

```python
from collections.abc import Callable
from functools import cmp_to_key
from typing import Any


def my_cmp_to_key(cmp: Callable[[Any, Any], int]) -> type:
    class Key:
        __slots__ = ("value",)

        def __init__(self, value: Any) -> None:
            self.value = value

        def __lt__(self, other: "Key") -> bool:
            return cmp(self.value, other.value) < 0

        def __eq__(self, other: object) -> bool:
            return isinstance(other, Key) and cmp(self.value, other.value) == 0

    return Key


def compare_versions(a: str, b: str) -> int:
    left = [int(part) for part in a.split(".")]
    right = [int(part) for part in b.split(".")]
    return (left > right) - (left < right)


versions = ["1.10.0", "1.2.3", "1.9.12", "1.2.10"]
mine = sorted(versions, key=my_cmp_to_key(compare_versions))
standard = sorted(versions, key=cmp_to_key(compare_versions))
print(mine)
print(mine == standard)
```

Результат:

```text
['1.2.3', '1.2.10', '1.9.12', '1.10.0']
True
```

`sorted()` потребує між ключами лише операції `<`, тож для сортування досить `__lt__`. Повернений клас і є адаптером: він обгортає кожне значення й перекладає запитання «чи менше?» на виклик функції порівняння старого стилю. Справжній `functools.cmp_to_key` визначає ще `__gt__`, `__le__` і `__ge__`, тому його ключі працюють і з `min()`, `max()` та іншими порівняннями.
