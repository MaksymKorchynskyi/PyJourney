# Замісник/Декоратор

**Замісник** (Proxy) і **Декоратор** (Decorator) — два структурні патерни, побудовані однаково: об'єкт-обгортка має той самий інтерфейс, що й об'єкт усередині, і пересилає йому виклики, попутно роблячи щось додаткове. Відрізняються вони метою. Замісник **контролює доступ** до об'єкта (створює його ліниво, кешує його відповіді, перевіряє права). Декоратор **додає об'єкту обов'язки**, і декоратори задумані так, щоб їх можна було нашаровувати в будь-яких комбінаціях. А ще в Python є синтаксис `@decorator`, пов'язаний із патерном Декоратор, але це не одне й те саме.

## Що ви дізнаєтесь

- Як замісник додає ліниве завантаження, кешування й контроль доступу, не змінюючи ні справжнього об'єкта, ні його клієнтів
- Як написати універсальний замісник-пересилач на `__getattr__` і де він ламається
- Коли замісник варто зробити підкласом сервісу, а не обгорткою
- Як патерн Декоратор замінює вибух кількості підкласів обгортками, які можна нашаровувати
- Чому порядок декораторів має значення
- Чим *патерн* Декоратор відрізняється від *синтаксису* `@decorator` у Python і як вони пов'язані
- Як відрізнити Замісник від Декоратора

## Замісник

### Суть патерна

**Замісник** (Proxy) підставляє замість іншого об'єкта (**сервісу**) його замінник. Замісник має той самий інтерфейс, що й сервіс, тож клієнти не можуть їх розрізнити, але він контролює доступ до сервісу: може щось зробити до чи після пересилання запиту або взагалі його не пересилати.

### Проблема

Інтернет-магазин показує ціни в гривнях, а курси валют надходять зі стороннього клієнта API. Клієнт повільний: під час створення він відкриває мережеве з'єднання, а кожен виклик `get_rate()` — це HTTP-запит. Сторінка товару з 30 цінами робить 30 однакових запитів, а з'єднання відкривається навіть для сторінок, на яких цін немає взагалі.

Можна додати кешування й ліниве створення в кожне місце, де використовується клієнт, але тоді той самий код буде скопійовано всюди. Можна додати їх у сам клас клієнта, але він належить сторонній бібліотеці, і змінити його ви не можете.

### Рішення

Створіть клас-**замісник** із тим самим інтерфейсом, що й у справжнього клієнта. Замісник зберігає посилання на сервіс, а коли надходить запит, спершу виконує власну роботу (створює сервіс під час першого звернення, заглядає в кеш) і лише за потреби делегує запит справжньому сервісу.

Оскільки замісник дотримується того самого інтерфейсу, його можна передати будь-якому коду, що очікує справжнього клієнта. Ні клієнтський код, ні сервіс не знають, що між ними стоїть замісник.

### Аналогія з життя

Банківська картка — замісник грошей на вашому рахунку. У магазині вона годиться для оплати так само, як готівка: ви нею «платите». Але картка додає контроль: перевіряє PIN-код, може заблокувати підозрілу покупку й переказує магазину гроші без того, щоб хтось носив мішок банкнот. Магазину байдуже, чим ви розрахувалися, карткою чи готівкою: обидві дотримуються одного інтерфейсу «оплата».

### Структура

```text
+--------+       +--------------------------------+
| Клієнт |------>| <<Protocol>> RatesService      |
+--------+       |--------------------------------|
                 | + get_rate(base, quote)        |
                 +--------------------------------+
                        ^                  ^
                        :                  :
  +-------------------------+   +--------------------------------+
  | RemoteRatesClient       |   | CachingRatesProxy              |
  | (сервіс)                |   |--------------------------------|
  |-------------------------|<----o _service: RemoteRatesClient  |
  | + get_rate(base, quote) |   | - _cache: dict                 |
  +-------------------------+   |--------------------------------|
                                | + get_rate(base, quote):       |
                                |     ліниво / кеш / перевірки   |
                                |     _service.get_rate(...)     |
                                +--------------------------------+
```

1. **Інтерфейс сервісу** оголошує, що вміє сервіс. Замісник мусить дотримуватися цього інтерфейсу, щоб видавати себе за сервіс.
2. **Сервіс** містить справжню бізнес-логіку.
3. **Замісник** зберігає посилання на сервіс. Він виконує власне завдання (ліниве створення, кешування, контроль доступу, журналювання) і передає запит далі. Часто замісник керує всім життєвим циклом свого сервісу.
4. **Клієнт** працює і з сервісом, і із замісником через той самий інтерфейс.

### Реалізація на Python

```python
from typing import Protocol


class RatesService(Protocol):
    def get_rate(self, base: str, quote: str) -> float: ...


class RemoteRatesClient:
    """Сторонній клієнт: повільний і дорогий, а змінити його код ми не можемо."""

    def __init__(self) -> None:
        print("RemoteRatesClient: opening a connection to the API...")
        self.requests = 0

    def get_rate(self, base: str, quote: str) -> float:
        self.requests += 1
        print(f"RemoteRatesClient: HTTP request #{self.requests} for {base}/{quote}")
        return {("USD", "UAH"): 41.5, ("EUR", "UAH"): 48.2}[(base, quote)]


class CachingRatesProxy:
    """Той самий інтерфейс, що й у справжнього клієнта, плюс ліниве створення й кеш."""

    def __init__(self) -> None:
        self._service: RemoteRatesClient | None = None
        self._cache: dict[tuple[str, str], float] = {}

    def _get_service(self) -> RemoteRatesClient:
        if self._service is None:  # віртуальний замісник: створюємо під час першого звернення
            self._service = RemoteRatesClient()
        return self._service

    def get_rate(self, base: str, quote: str) -> float:
        key = (base, quote)
        if key not in self._cache:  # кешувальний замісник
            self._cache[key] = self._get_service().get_rate(base, quote)
        return self._cache[key]


def show_prices(rates: RatesService, prices_usd: list[float]) -> None:
    """Клієнтський код: працює з будь-чим, що має get_rate()."""
    for price in prices_usd:
        print(f"  {price:>5} USD = {price * rates.get_rate('USD', 'UAH'):8.2f} UAH")


rates = CachingRatesProxy()
print("proxy created, no connection yet")
show_prices(rates, [10, 25, 99.9])
print("EUR/UAH:", rates.get_rate("EUR", "UAH"))
print("EUR/UAH:", rates.get_rate("EUR", "UAH"))
```

Результат:

```text
proxy created, no connection yet
RemoteRatesClient: opening a connection to the API...
RemoteRatesClient: HTTP request #1 for USD/UAH
     10 USD =   415.00 UAH
     25 USD =  1037.50 UAH
   99.9 USD =  4145.85 UAH
RemoteRatesClient: HTTP request #2 for EUR/UAH
EUR/UAH: 48.2
EUR/UAH: 48.2
```

Цей замісник поєднує дві класичні ролі. Як **віртуальний замісник** він відкладає створення дорогого клієнта до першого справжнього запиту. Як **кешувальний замісник** він сам відповідає на повторні запити: три ціни коштують одного HTTP-запиту. Функцію `show_prices()` писали для справжнього клієнта, і вона працює без змін.

> **Зверніть увагу:** справжньому кешувальному замісникові потрібна ще й **політика застарівання**: курси змінюються, і кеш, який нічого не забуває, віддає застарілі дані. Зберігайте разом зі значенням час його отримання або використовуйте кеш, що враховує час.

### План Б: замісник як підклас сервісу

Іноді інтерфейс виокремити неможливо: старий клієнтський код перевіряє конкретний клас через `isinstance()`, а переписати його весь немає змоги. Тоді замісник може **успадкувати** клас сервісу. Він задарма отримує весь інтерфейс, проходить перевірки `isinstance()` і викликає справжню реалізацію через `super()`, а не через збережене посилання:

```python
# Продовження попереднього прикладу
class CachedRatesClient(RemoteRatesClient):
    """План Б: замісник Є RemoteRatesClient і успадковує його інтерфейс."""

    def __init__(self) -> None:
        super().__init__()  # з'єднання відкривається одразу: жодного лінивого створення
        self._cache: dict[tuple[str, str], float] = {}

    def get_rate(self, base: str, quote: str) -> float:
        key = (base, quote)
        if key not in self._cache:
            self._cache[key] = super().get_rate(base, quote)
        return self._cache[key]


def legacy_report(client: RemoteRatesClient) -> None:
    """Старий код, який вимагає саме конкретний клас."""
    if not isinstance(client, RemoteRatesClient):
        raise TypeError("RemoteRatesClient required")
    show_prices(client, [10, 25])


try:
    legacy_report(CachingRatesProxy())
except TypeError as exc:
    print("TypeError:", exc)

legacy_report(CachedRatesClient())
```

Результат:

```text
TypeError: RemoteRatesClient required
RemoteRatesClient: opening a connection to the API...
RemoteRatesClient: HTTP request #1 for USD/UAH
     10 USD =   415.00 UAH
     25 USD =  1037.50 UAH
```

Ціна цього скорочення: замісник тепер прив'язаний до одного конкретного класу, не може обгорнути вже наявний об'єкт, а дорогий `__init__` сервісу виконується одразу, тож замісник-підклас не може бути лінивим (віртуальним). Коли є вибір, надавайте перевагу композиції.

### Практичний приклад: захисний замісник на `__getattr__`

Писати метод-пересилач для кожного методу сервісу втомливо. Метод `__getattr__` у Python викликається лише тоді, коли звичайний пошук атрибута зазнав невдачі, тож замісник може визначити методи, які хоче контролювати, а **все інше** пересилати автоматично:

```python
from typing import Any


class BankAccount:
    def __init__(self, owner: str, balance: float) -> None:
        self.owner = owner
        self.balance = balance

    def deposit(self, amount: float) -> None:
        self.balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount


class ProtectedAccount:
    """Захисний і журналювальний замісник, що автоматично пересилає все інше."""

    OWNER_ONLY = {"withdraw"}

    def __init__(self, account: BankAccount, user: str) -> None:
        self._account = account
        self._user = user

    def __getattr__(self, name: str) -> Any:
        # Викликається лише для атрибутів, яких НЕМАЄ в самого замісника
        attr = getattr(self._account, name)
        if name in self.OWNER_ONLY and self._user != self._account.owner:
            raise PermissionError(f"{self._user} may not call {name}()")
        if callable(attr):
            def logged(*args: Any, **kwargs: Any) -> Any:
                print(f"[audit] {self._user} -> {name}{args}")
                return attr(*args, **kwargs)
            return logged
        return attr


account = BankAccount(owner="olena", balance=1000)
as_owner = ProtectedAccount(account, user="olena")
as_cashier = ProtectedAccount(account, user="cashier")

as_cashier.deposit(250)
as_owner.withdraw(400)
try:
    as_cashier.withdraw(100)
except PermissionError as exc:
    print("denied:", exc)
print("balance seen through the proxy:", as_cashier.balance)
```

Результат:

```text
[audit] cashier -> deposit(250,)
[audit] olena -> withdraw(400,)
denied: cashier may not call withdraw()
balance seen through the proxy: 850
```

Цей **захисний замісник** перевіряє, хто що викликає, а заодно журналює виклики. Клас `BankAccount` нічого не знає ні про користувачів, ні про журнал аудиту. Універсальне пересилання зручне, але має межі: неявні виклики спеціальних методів, як-от `len(x)` чи `x + y`, оминають `__getattr__`, а `isinstance(as_owner, BankAccount)` дає `False`. Див. «Типові помилки».

### Замісники в стандартній бібліотеці

```python
from functools import lru_cache
from types import MappingProxyType

# 1. Захисний замісник для словника: лише читання
settings = {"debug": False}
public_settings = MappingProxyType(settings)
print(public_settings["debug"])
try:
    public_settings["debug"] = True
except TypeError as exc:
    print("TypeError:", exc)
settings["debug"] = True          # власник змінює справжній словник...
print(public_settings["debug"])   # ...а замісник показує актуальне значення


# 2. Кешувальний замісник для функції
@lru_cache(maxsize=128)
def slow_square(n: int) -> int:
    print(f"computing {n}**2")
    return n * n


print(slow_square(12), slow_square(12))
print(slow_square.cache_info())
```

Результат:

```text
False
TypeError: 'mappingproxy' object does not support item assignment
True
computing 12**2
144 144
CacheInfo(hits=1, misses=1, maxsize=128, currsize=1)
```

`types.MappingProxyType` — саме те, що каже його назва: захисний замісник, який дає доступ лише на читання до словника, який власник і далі може змінювати. Сам Python використовує його для `__dict__` класів. `functools.lru_cache` обгортає функцію кешувальним замісником. Варто знати й інші: `weakref.proxy()` (замісник, що не тримає свою ціль живою) і `multiprocessing.managers` (віддалені замісники для об'єктів в іншому процесі).

### Різновиди замісників

| Різновид | Що робить | Приклад |
|---|---|---|
| Віртуальний замісник | Створює важкий об'єкт лише тоді, коли той уперше знадобиться | `CachingRatesProxy._get_service()`, ліниві зображення |
| Кешувальний замісник | Запам'ятовує результати повторюваних запитів | `functools.lru_cache`, HTTP-кеш |
| Захисний замісник | Перевіряє права перед пересиланням | `ProtectedAccount`, `MappingProxyType` |
| Віддалений замісник | Представляє об'єкт, що живе в іншому процесі чи на іншій машині | RPC-клієнти, менеджери `multiprocessing` |
| Журналювальний замісник | Записує кожен запит до сервісу | частина `ProtectedAccount`, що веде аудит |
| Розумне посилання | Стежить, хто користується сервісом, і звільняє його, коли ним ніхто не користується | з'єднання з лічильником посилань, `weakref.proxy` |

> **Порада:** як розпізнати замісник у наявному коді: він має ті самі методи, що й якийсь інший об'єкт, і кожен із них після додаткової роботи (або рішення запит не пропускати) зрештою викликає той самий метод цього об'єкта, або `super()`, якщо замісник — підклас сервісу.

### Коли застосовувати Замісник

- **Ліниве створення:** важкий об'єкт потрібен лише іноді, і створювати його під час запуску означає марнувати ресурси.
- **Контроль доступу:** користуватися сервісом чи деякими його методами можуть лише певні клієнти.
- **Віддалений сервіс:** справжній об'єкт живе на іншому сервері, а замісник приховує подробиці роботи з мережею.
- **Журналювання чи аудит** запитів до сервісу.
- **Кешування** результатів повторюваних запитів, особливо великих чи дорогих.
- **Керування життєвим циклом:** звільнити сервіс, коли ним більше не користується жоден клієнт.

### Кроки реалізації Замісника

1. Якщо інтерфейсу сервісу немає, опишіть його (`Protocol` працює, не чіпаючи класу сервісу). Якщо це неможливо, зробіть замісник підкласом сервісу, щоб він успадкував інтерфейс (див. «План Б» вище).
2. Створіть клас замісника з полем, що посилається на сервіс. Зазвичай замісник сам створює сервіс і керує його життєвим циклом; рідше клієнт передає сервіс у конструктор.
3. Реалізуйте методи замісника: виконайте власну роботу замісника, а потім делегуйте сервісу.
4. Подумайте про фабричну функцію, яка вирішує, що отримає клієнт: замісник чи справжній сервіс (наприклад, залежно від конфігурації).
5. Подумайте про ліниве створення сервісу.

### Переваги та недоліки Замісника

**Переваги:**

- Ви контролюєте сервіс так, що клієнти про це не знають.
- Ви можете керувати життєвим циклом сервісу, навіть коли клієнтів це не обходить.
- Замісник працює, навіть коли сервіс ще не готовий чи тимчасово недоступний (він може відповісти з кешу).
- *Принцип відкритості/закритості*: нові замісники можна додавати, не змінюючи ні сервісу, ні клієнтів.

**Недоліки:**

- Більше класів і зайвий рівень непрямості.
- Відповідь може затримуватися (перший запит через лінивий замісник, перевірки прав).
- Прозорий замісник може приховувати важливу поведінку: застарілий кеш чи «проковтнуті» виклики важко помітити.

### Відносини з іншими патернами

- **Адаптер, Замісник, Декоратор.** Адаптер надає об'єкту *інший* інтерфейс. Замісник зберігає *той самий* інтерфейс. Декоратор зберігає той самий або надає *розширений* інтерфейс.
- **Фасад проти Замісника.** Обидва стоять перед складною сутністю й можуть самі її ініціалізувати. Фасад пропонує новий, простіший інтерфейс, а Замісник має той самий інтерфейс, що й сервіс, тому їх можна підміняти одне одним.
- **Декоратор проти Замісника.** Однакова структура, різна мета: див. розділ «Замісник проти Декоратора» нижче.

## Декоратор

### Суть патерна

**Декоратор** (Decorator, також відомий як **Обгортка**, Wrapper) приєднує до об'єкта нову поведінку, поміщаючи його в об'єкт-обгортку з тим самим інтерфейсом. Обгортки можуть обгортати інші обгортки, тож поведінки комбінуються нашаровуванням, і відбувається це під час виконання.

### Проблема

Ви зберігаєте налаштування користувачів через `DataSource` з методами `write()` і `read()`. Різним розгортанням потрібні різні доповнення:

- стискати дані, щоб заощадити місце;
- кодувати їх у Base64, щоб їх можна було зберігати в суто текстовому місці (JSON, змінні оточення);
- журналювати кожен запис у налагоджувальних збірках;
- шифрувати їх у продакшені.

Підхід через успадкування починається невинно: `CompressedDataSource` і `Base64DataSource`. Потім комусь потрібне і те, і те, і з'являється `CompressedBase64DataSource`. Додайте журналювання й шифрування, і кожна комбінація потребуватиме власного класу: з чотирма незалежними можливостями це до 15 підкласів, а ще ж має значення й порядок. Це називають **комбінаторним вибухом** підкласів. До того ж успадкування статичне: не можна додати стиснення до вже наявного об'єкта під час виконання, можна лише створити інший об'єкт іншого класу.

Множинне успадкування в Python пом'якшує біль, але не лікує його. З міксинами `class CompressedBase64Source(CompressionMixin, Base64Mixin, FileDataSource)` вміщується в один рядок, проте кожну комбінацію (і кожен порядок) однаково треба оголосити як клас заздалегідь, ще до того, як програма дізнається, чого вимагатиме конфігурація.

### Рішення

Використайте **композицію** замість успадкування. *Обгортка* зберігає посилання на інший об'єкт із тим самим інтерфейсом, пересилає йому запити й додає власну поведінку до або після пересилання. Оскільки обгортка теж дотримується цього інтерфейсу, вона може обгортати не лише базовий об'єкт, а й інші обгортки.

Залиште базову поведінку (зберігання байтів) у простому **конкретному компоненті**, а кожну необов'язкову можливість перетворіть на **декоратор**. Клієнт збирає саме ту комбінацію, яка йому потрібна:

```text
CompressionDecorator( Base64Decorator( MemoryDataSource() ) )
```

Клієнт працює з найзовнішнім декоратором. Оскільки всі шари мають спільний інтерфейс, решті коду байдуже, з чим вона має справу: із простим джерелом даних чи зі стеком із п'яти декораторів.

### Аналогія з життя

Згадайте смартфон. Ви вдягаєте на нього захисний чохол, наклеюєте захисне скло, а може, ще й прикріплюєте ззаду кишеньку для карток. Кожен шар щось додає (захист від падінь, від подряпин, місце для карток), а телефон працює так само: ви й далі дзвоните й торкаєтеся екрана. Шари не є частиною телефона, і будь-який із них можна додати чи зняти будь-коли.

### Структура

```text
                +------------------------------+
  Клієнт ------>| <<Protocol>> DataSource      |<--------------+
                |------------------------------|               |
                | + write(data)                |               | обгортає
                | + read() -> bytes            |               | будь-який
                +------------------------------+               | DataSource
                      ^                   ^                    |
                      :                   :                    |
  +----------------------+   +--------------------------------+|
  | MemoryDataSource     |   | DataSourceDecorator            ||
  | (конкр. компонент)   |   |--------------------------------||
  |----------------------|   | - _wrappee: DataSource  o-------+
  | + write(data)        |   | + write(data) -> _wrappee      |
  | + read()             |   | + read()      -> _wrappee      |
  +----------------------+   +--------------------------------+
                                  ^                    ^
                                  |                    |
                  +----------------------+   +-------------------+
                  | CompressionDecorator |   | Base64Decorator   |
                  | + write / read       |   | + write / read    |
                  +----------------------+   +-------------------+
```

1. **Компонент** оголошує спільний інтерфейс для обгорток і обгорнутих об'єктів.
2. **Конкретний компонент** визначає базову поведінку, яку декоратори можуть змінювати.
3. **Базовий декоратор** зберігає посилання на обгорнутий об'єкт, оголошене з типом інтерфейсу компонента, тож туди можна покласти і конкретні компоненти, і інші декоратори. За замовчуванням він делегує кожну операцію обгорнутому об'єкту.
4. **Конкретні декоратори** додають поведінку до або після виклику методу базового декоратора (який пересилає виклик обгорнутому об'єкту).
5. **Клієнт** обгортає компоненти в стільки шарів, скільки потрібно, і працює з усіма ними через інтерфейс компонента.

### Реалізація на Python

```python
import base64
import zlib
from typing import Protocol


class DataSource(Protocol):
    def write(self, data: bytes) -> None: ...
    def read(self) -> bytes: ...


class MemoryDataSource:
    """Конкретний компонент: зберігає байти як є (у реальному житті — файл чи БД)."""

    def __init__(self) -> None:
        self.stored = b""

    def write(self, data: bytes) -> None:
        self.stored = data

    def read(self) -> bytes:
        return self.stored


class DataSourceDecorator:
    """Базовий декоратор: той самий інтерфейс, усе делегує обгорнутому об'єкту."""

    def __init__(self, wrappee: DataSource) -> None:
        self._wrappee = wrappee

    def write(self, data: bytes) -> None:
        self._wrappee.write(data)

    def read(self) -> bytes:
        return self._wrappee.read()


class CompressionDecorator(DataSourceDecorator):
    def write(self, data: bytes) -> None:
        super().write(zlib.compress(data))

    def read(self) -> bytes:
        return zlib.decompress(super().read())


class Base64Decorator(DataSourceDecorator):
    """Робить двійкові дані придатними для суто текстових сховищ (JSON, e-mail, змінні оточення)."""

    def write(self, data: bytes) -> None:
        super().write(base64.b64encode(data))

    def read(self) -> bytes:
        return base64.b64decode(super().read())


payload = b"salary;" * 20  # 140 байтів, що багато разів повторюються


def store(label: str, source: DataSource, disk: MemoryDataSource) -> None:
    source.write(payload)
    print(f"{label:<26} {len(disk.stored):>3} bytes, "
          f"text-safe={disk.stored.isascii()}, round-trip={source.read() == payload}")


disk = MemoryDataSource()
store("disk", disk, disk)

disk = MemoryDataSource()
store("Compression(Base64(disk))", CompressionDecorator(Base64Decorator(disk)), disk)
print("  stored:", disk.stored.decode())

disk = MemoryDataSource()
store("Base64(Compression(disk))", Base64Decorator(CompressionDecorator(disk)), disk)
```

Результат:

```text
disk                       140 bytes, text-safe=True, round-trip=True
Compression(Base64(disk))   24 bytes, text-safe=True, round-trip=True
  stored: eJwrTsxJLKq0Lh4MFABWYzeN
Base64(Compression(disk))   41 bytes, text-safe=False, round-trip=True
```

Ось як запис проходить крізь `CompressionDecorator(Base64Decorator(disk))`: зовнішній декоратор стискає дані й передає їх усередину, декоратор Base64 кодує стиснені байти, а диск зберігає ASCII-текст. Читання йде у зворотному напрямку: спершу декодування, потім розпакування.

Останній рядок показує, що **порядок має значення**. Якщо поміняти шари місцями, Base64 спрацює першим, а стиснення — другим, тож на диск потраплять стиснені двійкові дані. Запис і зворотне читання й далі працюють, але збережене значення вже не безпечне для тексту й майже вдвічі більше. Декоратори незалежні, але їхня комбінація — проєктне рішення, яке клієнт має ухвалювати свідомо.

У реальному застосунку стек зазвичай збирають в одному місці з конфігурації, а код, що користується джерелом даних, так і не дізнається, що всередині. Зверніть увагу на порядок інструкцій `if`: шар, що має бути **найближче до сховища**, обгортається **першим**, а найзовнішній шар першим перетворює дані під час `write()`:

```python
# Продовження попереднього прикладу
class SettingsStore:
    """Клієнтський код: нічого не знає про стиснення чи кодування."""

    def __init__(self, source: DataSource) -> None:
        self._source = source

    def save(self, text: str) -> None:
        self._source.write(text.encode("utf-8"))

    def load(self) -> str:
        return self._source.read().decode("utf-8")


def build_source(disk: DataSource, *, compress: bool, text_safe: bool) -> DataSource:
    """Збирає стек із конфігурації, починаючи з найглибшого шару."""
    source = disk
    if text_safe:
        source = Base64Decorator(source)       # має бути безпосередньо над сховищем
    if compress:
        source = CompressionDecorator(source)  # найзовнішній: під час запису працює першим
    return source


for config in ({"compress": False, "text_safe": False},
               {"compress": True, "text_safe": True}):
    disk = MemoryDataSource()
    settings = SettingsStore(build_source(disk, **config))
    settings.save("theme=dark;lang=uk;" * 3)
    print(config)
    print("  stored:", disk.stored)
    print("  loaded:", settings.load())
```

Результат:

```text
{'compress': False, 'text_safe': False}
  stored: b'theme=dark;lang=uk;theme=dark;lang=uk;theme=dark;lang=uk;'
  loaded: theme=dark;lang=uk;theme=dark;lang=uk;theme=dark;lang=uk;
{'compress': True, 'text_safe': True}
  stored: b'eJwryUjNTbVNSSzKts5JzEu3Lc22LiFKCAB0dxV2'
  loaded: theme=dark;lang=uk;theme=dark;lang=uk;theme=dark;lang=uk;
```

`SettingsStore` написано один раз, і він працює і з «голим» сховищем, і з будь-яким стеком декораторів, бо всі вони дотримуються інтерфейсу `DataSource`.

> **Порада:** як розпізнати декоратор у наявному коді: його конструктор приймає об'єкт того самого інтерфейсу, який реалізує сам клас. `CompressionDecorator(wrappee: DataSource)` сам є `DataSource`, а `io.TextIOWrapper(buffer)` сам є потоком.

### Практичний приклад: шари повторних спроб і журналювання

Мережевий код — класичне місце для декораторів: повторні спроби, журналювання, вимірювання часу, обмеження частоти запитів і кешування — це незалежні аспекти, які в продакшені, у тестах і під час налагодження хочеться комбінувати по-різному:

```python
from typing import Protocol


class Fetcher(Protocol):
    def fetch(self, url: str) -> str: ...


class FlakyFetcher:
    """Конкретний компонент: «мережа», що збоїть задану кількість разів."""

    def __init__(self, failures: int) -> None:
        self.failures_left = failures

    def fetch(self, url: str) -> str:
        if self.failures_left > 0:
            self.failures_left -= 1
            raise ConnectionError("network glitch")
        return f"<html>{url}</html>"


class FetcherDecorator:
    def __init__(self, inner: Fetcher) -> None:
        self._inner = inner

    def fetch(self, url: str) -> str:
        return self._inner.fetch(url)


class Retry(FetcherDecorator):
    def __init__(self, inner: Fetcher, attempts: int = 3) -> None:
        super().__init__(inner)
        self.attempts = attempts

    def fetch(self, url: str) -> str:
        for attempt in range(1, self.attempts + 1):
            try:
                return super().fetch(url)
            except ConnectionError as exc:
                print(f"  Retry: attempt {attempt} failed ({exc})")
        raise ConnectionError(f"gave up after {self.attempts} attempts")


class Logging(FetcherDecorator):
    def fetch(self, url: str) -> str:
        print(f"  Logging: GET {url}")
        try:
            result = super().fetch(url)
        except ConnectionError:
            print("  Logging: failed")
            raise
        print(f"  Logging: got {len(result)} chars")
        return result


print("Logging(Retry(...)): one log entry for the whole operation")
Logging(Retry(FlakyFetcher(failures=2))).fetch("/news")

print("Retry(Logging(...)): every attempt is logged")
Retry(Logging(FlakyFetcher(failures=2))).fetch("/news")
```

Результат:

```text
Logging(Retry(...)): one log entry for the whole operation
  Logging: GET /news
  Retry: attempt 1 failed (network glitch)
  Retry: attempt 2 failed (network glitch)
  Logging: got 18 chars
Retry(Logging(...)): every attempt is logged
  Logging: GET /news
  Logging: failed
  Retry: attempt 1 failed (network glitch)
  Logging: GET /news
  Logging: failed
  Retry: attempt 2 failed (network glitch)
  Logging: GET /news
  Logging: got 18 chars
```

Ті самі два декоратори дають дві різні поведінки залежно від порядку. Зовнішнє журналювання описує операцію так, як її бачить той, хто викликає. Внутрішнє фіксує кожну мережеву спробу. Ні `Retry`, ні `Logging` не знають одне про одного, а `FlakyFetcher` не знає ні про кого з них.

### Декоратор у стандартній бібліотеці: потоки введення-виведення

Система введення-виведення Python — це стек декораторів. `io.TextIOWrapper` перетворює текст на байти, `gzip.GzipFile` стискає байти, і обидва приймають інший файлоподібний об'єкт, який обгортають:

```python
import gzip
import io

buffer = io.BytesIO()  # конкретний компонент: сирі байти в пам'яті

# TextIOWrapper (str -> bytes) обгортає GzipFile (стиснення), а той обгортає BytesIO
with io.TextIOWrapper(gzip.GzipFile(fileobj=buffer, mode="wb"), encoding="utf-8") as f:
    f.write("Привіт, PyJourney!\n" * 50)

print("compressed size:", len(buffer.getvalue()), "bytes")

buffer.seek(0)
with io.TextIOWrapper(gzip.GzipFile(fileobj=buffer, mode="rb"), encoding="utf-8") as f:
    lines = f.readlines()
print(len(lines), "lines, first:", lines[0].strip())
```

Результат:

```text
compressed size: 64 bytes
50 lines, first: Привіт, PyJourney!
```

Кожен шар — файлоподібний об'єкт, тож код, що записує рядки, не знає, куди саме пише: у звичайний файл, у пам'ять чи крізь стиснення. Сама функція `open()` повертає такий стек: `TextIOWrapper` навколо `BufferedReader` навколо `FileIO`.

### Коли застосовувати Декоратор

- Потрібно додавати поведінку окремим об'єктам під час виконання, не ламаючи коду, що ними користується.
- Поведінки — це незалежні шари, які треба комбінувати по-різному.
- Розширювати через успадкування непрактично (забагато комбінацій) або неможливо (клас закритий для змін чи походить із бібліотеки).

### Кроки реалізації Декоратора

1. Переконайтеся, що предметну область можна подати як базовий компонент із необов'язковими шарами поверх нього.
2. Визначте методи, спільні для компонента й шарів, і оголосіть їх в інтерфейсі компонента (`Protocol` або ABC).
3. Створіть конкретний компонент із базовою поведінкою.
4. Створіть базовий декоратор, який зберігає обгорнутий об'єкт (з типом інтерфейсу) і пересилає йому кожен метод.
5. Створіть конкретні декоратори, що розширюють базовий декоратор і додають поведінку до або після виклику `super()`.
6. Нехай стек збирає клієнт. Невелика фабрична функція може будувати типові стеки з конфігурації.

### Переваги та недоліки Декоратора

**Переваги:**

- Поведінку можна розширювати без нових підкласів.
- Обов'язки можна додавати об'єкту чи знімати з нього під час виконання.
- Кілька поведінок можна поєднати, обгорнувши об'єкт кількома декораторами.
- *Принцип єдиного обов'язку*: монолітний клас із багатьма варіантами поведінки розпадається на невеликі зосереджені класи.

**Недоліки:**

- Прибрати конкретну обгортку із середини стека незручно.
- Поведінка може залежати від порядку декораторів, а писати декоратори, незалежні від порядку, важко.
- Код, що будує стек (`A(B(C(D(x))))`), буває важко читати.
- Багато дрібних об'єктів з однаковим інтерфейсом ускладнюють налагодження й подовжують трасування стека.

### Відносини з іншими патернами

- **Адаптер проти Декоратора.** Адаптер змінює інтерфейс об'єкта. Декоратор зберігає чи розширює його й підтримує рекурсивну композицію, на яку Адаптер не здатен.
- **Ланцюжок обов'язків проти Декоратора.** Обидва передають запит крізь ланцюжок об'єктів. Обробники Ланцюжка обов'язків можуть зупинити запит у будь-якій точці й діють незалежно один від одного. Декоратори розширюють поведінку, зберігаючи її узгодженою з інтерфейсом, і завжди передають запит далі.
- **Компонувальник проти Декоратора.** Обидва спираються на рекурсивну композицію. Декоратор має рівно один дочірній об'єкт і додає обов'язки. Компонувальник має багато дочірніх об'єктів і лише підсумовує їхні результати. Декоратор може обгорнути окремий вузол дерева Компонувальника.
- **Прототип** допомагає, коли складні стеки декораторів треба клонувати, а не будувати заново.
- **Стратегія проти Декоратора.** Декоратор змінює «шкіру» об'єкта, а Стратегія — його «нутрощі».

## Патерн Декоратор і синтаксис `@decorator` у Python

Слова однакові, ідеї перетинаються, але це не одне й те саме.

**Що насправді таке `@decorator`.** Це синтаксис, який застосовує викликуваний об'єкт до функції чи класу одразу після їхнього визначення (докладно його розбирає розділ про декоратори, починаючи з теми Python Decorators):

```text
@retry(attempts=3)              означає те саме, що й       def fetch(url): ...
def fetch(url): ...                                         fetch = retry(attempts=3)(fetch)
```

Те, що повертає декоратор, займає місце початкового імені. Ось декоратор функції, що додає повторні спроби:

```python
import functools


def retry(attempts: int):
    def decorator(func):
        @functools.wraps(func)  # зберігає ім'я, docstring і __wrapped__
        def wrapper(*args, **kwargs):
            for attempt in range(1, attempts + 1):
                try:
                    return func(*args, **kwargs)
                except ConnectionError as exc:
                    print(f"  attempt {attempt} failed ({exc})")
            raise ConnectionError(f"gave up after {attempts} attempts")
        return wrapper
    return decorator


failures = iter([True, True, False])


@retry(attempts=3)          # те саме, що fetch = retry(attempts=3)(fetch)
def fetch(url: str) -> str:
    """Download a page."""
    if next(failures):
        raise ConnectionError("network glitch")
    return f"<html>{url}</html>"


print(fetch("/news"))
print(fetch.__name__, "|", fetch.__doc__)
print(fetch.__wrapped__.__name__, fetch.__wrapped__ is fetch)
```

Результат:

```text
  attempt 1 failed (network glitch)
  attempt 2 failed (network glitch)
<html>/news</html>
fetch | Download a page.
fetch False
```

**Як вони пов'язані.** Декоратор функції на кшталт `retry` *і є* патерном Декоратор, застосованим до одного викликуваного об'єкта. «Інтерфейс» тут — сигнатура виклику: `wrapper` приймає ті самі аргументи й повертає результат того самого виду, делегує обгорнутій функції, додає поведінку навколо виклику, і такі декоратори можна нашаровувати. `functools.wraps` — завершальний штрих, завдяки якому обгортка схожа на оригінал (той самий `__name__`, `__doc__` і посилання `__wrapped__` на нього).

**Чим вони відрізняються.**

| | Патерн Декоратор | Синтаксис `@decorator` |
|---|---|---|
| Що обгортається | Об'єкт з інтерфейсом, часто з кількома методами | Функція, метод або клас |
| Коли | Під час виконання, коли вирішить клієнт, для кожного об'єкта окремо | Зазвичай один раз, коли виконується інструкція `def`/`class`; впливає на кожен виклик |
| Хто компонує | Клієнтський код, що будує об'єкт | Автор функції |
| Механізм | Клас-обгортка, що зберігає посилання | Будь-який викликуваний об'єкт, що приймає функцію чи клас і щось повертає |
| Чи зберігає інтерфейс? | Завжди, за визначенням | Не обов'язково |

Останній рядок важливий: багато з того, що пишуть через `@`, — зовсім не патерн Декоратор.

- `@functools.lru_cache` обгортає функцію й зберігає її інтерфейс, але його мета — кешування, тож він ближчий до **кешувального замісника**.
- `@dataclass` нічого не обгортає. Він додає класу методи й повертає **той самий клас**: це метапрограмування.
- `@app.route("/")` у Flask реєструє функцію в таблиці маршрутів і повертає її без змін: це **реєстр**.
- `@property` і `@classmethod` перетворюють функцію на **дескриптор**.

І навпаки: патерн можна застосувати й без синтаксису `@`. Декоратор функції — звичайний викликуваний об'єкт, тож ним можна декорувати **один об'єкт під час виконання**, а саме про це й ідеться в патерні:

```python
import functools


def log_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"-> {func.__name__}{args}")
        return func(*args, **kwargs)
    return wrapper


class Calculator:
    def add(self, a: int, b: int) -> int:
        return a + b


calc = Calculator()
calc.add = log_calls(calc.add)   # декоруємо ОДИН об'єкт під час виконання, без @
print(calc.add(2, 3))
print(Calculator().add(2, 3))    # інших екземплярів це не стосується
```

Результат:

```text
-> add(2, 3)
5
5
```

**Практичне правило:** використовуйте декоратор функції (`@`), коли поведінка має стосуватися *кожного* виклику функції і вирішує це її автор. Використовуйте патерн Декоратор (класи-обгортки), коли *клієнт* має збирати поведінки для кожного об'єкта окремо під час виконання або коли інтерфейс має кілька методів, які треба обгорнути узгоджено.

## Замісник проти Декоратора

Код обох патернів може бути буквально однаковим: клас, що зберігає посилання на об'єкт із тим самим інтерфейсом і пересилає йому виклики. Різниця — у **меті** і в тому, **хто керує**.

| Питання | Замісник | Декоратор |
|---|---|---|
| Мета | Контролювати доступ до сервісу | Додати об'єкту обов'язки |
| Хто створює обгорнутий об'єкт? | Часто сам замісник (ліниво) або код налаштування, прихований від клієнта | Завжди клієнт, який компонує стек |
| Чи знає клієнт про обгортку? | Зазвичай ні: замісник прозорий | Так: клієнт будує її свідомо |
| Скільки шарів? | Зазвичай один | Кілька, і це задумано: суть саме в нашаровуванні |
| Інтерфейс | Точно такий, як у сервісу | Той самий, іноді розширений |
| Типові завдання | Ліниве завантаження, кешування, права доступу, віддалений доступ, розумні посилання | Стиснення, шифрування, форматування, повторні спроби, метрики в будь-якій комбінації |

Як вирішити:

- Якщо обгортка існує, щоб **охороняти справжній об'єкт чи керувати ним** (чи створювати його, хто може його викликати, чи потрібен виклик узагалі), це Замісник.
- Якщо обгортка існує, щоб **додати можливість**, яку клієнт може поєднати з іншими можливостями, це Декоратор.
- Кешувальна обгортка може бути і тим, і тим. Якщо застосунок непомітно видає кожному клієнтові кешований сервіс, це кешувальний замісник. Якщо клієнт свідомо будує `Logging(Cache(Retry(fetcher)))`, кеш — лише один декоратор серед інших.

## Типові помилки

- **Очікувати, що `__getattr__` пересилатиме спеціальні методи.** Спеціальні методи, як-от `__len__`, `__iter__` і `__add__`, Python шукає в **типі**, а не в екземплярі, тому неявні виклики (`len(x)`, `for`, `+`) оминають `__getattr__`:

  ```python
  class ListProxy:
      def __init__(self, target: list) -> None:
          self._target = target

      def __getattr__(self, name: str):
          return getattr(self._target, name)


  proxy = ListProxy([1, 2, 2, 3])
  print(proxy.count(2))            # звичайні методи пересилаються
  print(proxy.__len__())           # явний пошук атрибута теж працює
  try:
      print(len(proxy))            # але len() шукає __len__ у ТИПІ
  except TypeError as exc:
      print("TypeError:", exc)
  ```

  Результат:

  ```text
  2
  4
  TypeError: object of type 'ListProxy' has no len()
  ```

  Потрібні спеціальні методи визначайте в класі замісника явно (`def __len__(self): return len(self._target)`).

- **Нескінченна рекурсія в `__getattr__`.** Коли об'єкт створюється без `__init__` (через `copy` чи `pickle`), атрибута `self._target` ще немає, тож його читання знову викликає `__getattr__`, і так без кінця:

  ```python
  import copy


  class Proxy:
      def __init__(self, target: object) -> None:
          self._target = target

      def __getattr__(self, name: str):
          return getattr(self._target, name)  # ПОМИЛКА: self._target може ще не існувати


  try:
      copy.copy(Proxy([1, 2]))
  except RecursionError:
      print("RecursionError")


  class SafeProxy(Proxy):
      def __getattr__(self, name: str):
          if name.startswith("__") or name == "_target":
              raise AttributeError(name)  # не пересилаємо спеціальні й службові імена
          return getattr(self._target, name)


  clone = copy.copy(SafeProxy([1, 2]))
  print(clone.count(1))
  ```

  Результат:

  ```text
  RecursionError
  1
  ```

- **Клієнтський код, що перевіряє конкретні класи.** `isinstance(source, MemoryDataSource)` дає `False` для декорованого об'єкта чи об'єкта за замісником. Залежте від інтерфейсу (`Protocol`, качина типізація), а не від конкретного класу.
- **Базовий декоратор, що забув метод.** Якби `DataSourceDecorator` пересилав лише `write()`, кожен декорований об'єкт утратив би `read()`. Базовий декоратор мусить пересилати **весь** інтерфейс.
- **Забутий `functools.wraps`.** Без нього обгортка називається `wrapper` і не має docstring, а інструменти, що покладаються на `__name__`, `__doc__` чи `__wrapped__` (журналювання, документація, `inspect.signature`), бачать не ту функцію.
- **Ігнорувати порядок декораторів.** `Compression(Base64(x))` і `Base64(Compression(x))` зберігають різні дані. Задокументуйте потрібний порядок або будуйте стеки в одній фабричній функції.
- **Замісник, що непомітно змінює семантику.** Кеш без застарівання повертає застарілі дані, а лінивий замісник може згенерувати помилку з'єднання в несподіваний момент. Робіть таку поведінку явною в назвах і документації.

## Підсумок

- Замісник має той самий інтерфейс, що й його сервіс, і контролює доступ до нього: ліниве створення, кешування, права доступу, віддалені виклики, журналювання.
- Якщо інтерфейс виокремити не вдається, замісник може бути підкласом сервісу, але тоді він утрачає лінивість і змогу обгортати вже наявні об'єкти.
- `__getattr__` спрощує універсальне пересилання, але спеціальні методи його оминають, а необережне використання може призвести до нескінченної рекурсії.
- Декоратор обгортає об'єкт із тим самим інтерфейсом, щоб додати обов'язок. Декоратори нашаровуються, і комбінацію клієнт обирає під час виконання.
- Порядок декораторів — частина поведінки.
- У стандартній бібліотеці повно і того, і того: `MappingProxyType`, `lru_cache` і `weakref.proxy` — замісники, а потоки `io`/`gzip` утворюють стеки декораторів.
- Синтаксис `@decorator` у Python означає «замінити цю функцію результатом виклику декоратора з нею». Декоратор-обгортка функції — це патерн Декоратор, застосований до одного викликуваного об'єкта, але багато `@`-декораторів (`@dataclass`, `@property`, реєстрація маршрутів) — зовсім не цей патерн.
- Замісник і Декоратор можуть мати однаковий код. Замісник — про **контроль**, і зазвичай клієнт його не помічає. Декоратор — про **додавання можливостей**, і його компонує сам клієнт.

## Практика

### Вправа 1: Ліниві зображення

`RealImage` завантажує свій файл із диска в конструкторі, а це повільно. Галерея створює багато зображень, але користувач переглядає лише кілька. Напишіть віртуальний замісник `LazyImage` з тим самим інтерфейсом (атрибут `filename` і метод `display() -> str`), який створює `RealImage` лише під час першого виклику `display()`, а далі використовує вже створений об'єкт. Створіть галерею з трьох лінивих зображень і двічі покажіть одне з них.

### Вправа 2: Декоратори форматування тексту

Створіть компонент `PlainText(content)` з методом `render() -> str`, базовий `TextDecorator` і три декоратори: `Bold` (обгортає текст у `**`), `Italic` (обгортає його в `*`) і `Stripped` (прибирає пробіли на краях). Відобразіть `"  design patterns  "` у кількох комбінаціях і покажіть, що `Bold(Stripped(x))` і `Stripped(Bold(x))` дають різні результати.

### Вправа 3: Декоратор, що рахує виклики

Напишіть декоратор функції `count_calls`, який рахує виклики в атрибуті `calls` обгортки й зберігає ім'я та docstring обгорнутої функції. Застосуйте його через `@` до функції `greet(name)`. Потім, **не змінюючи** класу `Repository`, застосуйте його під час виконання до методу `find` одного екземпляра `Repository`, викличте метод тричі й покажіть, що сам клас не змінився.

## Розв'язки

### Вправа 1

```python
from typing import Protocol


class Image(Protocol):
    filename: str

    def display(self) -> str: ...


class RealImage:
    def __init__(self, filename: str) -> None:
        self.filename = filename
        print(f"loading {filename} from disk...")  # дорога операція

    def display(self) -> str:
        return f"[pixels of {self.filename}]"


class LazyImage:
    """Віртуальний замісник: створюється дешево, справжнє зображення вантажить під час першого display()."""

    def __init__(self, filename: str) -> None:
        self.filename = filename
        self._real: RealImage | None = None

    def display(self) -> str:
        if self._real is None:
            self._real = RealImage(self.filename)
        return self._real.display()


gallery: list[Image] = [LazyImage(f"photo{i}.jpg") for i in range(1, 4)]
print("gallery ready:", [image.filename for image in gallery])
print(gallery[1].display())
print(gallery[1].display())   # уже завантажено
```

Результат:

```text
gallery ready: ['photo1.jpg', 'photo2.jpg', 'photo3.jpg']
loading photo2.jpg from disk...
[pixels of photo2.jpg]
[pixels of photo2.jpg]
```

Завантажилося лише те зображення, яке справді показали, і лише один раз. Код галереї типізовано протоколом `Image`, тож він так само прийняв би й `RealImage`.

### Вправа 2

```python
from typing import Protocol


class Text(Protocol):
    def render(self) -> str: ...


class PlainText:
    def __init__(self, content: str) -> None:
        self.content = content

    def render(self) -> str:
        return self.content


class TextDecorator:
    def __init__(self, inner: Text) -> None:
        self._inner = inner

    def render(self) -> str:
        return self._inner.render()


class Bold(TextDecorator):
    def render(self) -> str:
        return f"**{super().render()}**"


class Italic(TextDecorator):
    def render(self) -> str:
        return f"*{super().render()}*"


class Stripped(TextDecorator):
    def render(self) -> str:
        return super().render().strip()


raw = PlainText("  design patterns  ")
print(repr(Bold(raw).render()))
print(repr(Bold(Stripped(raw)).render()))
print(repr(Italic(Bold(Stripped(raw))).render()))
print(repr(Stripped(Bold(raw)).render()))   # порядок має значення
```

Результат:

```text
'**  design patterns  **'
'**design patterns**'
'***design patterns***'
'**  design patterns  **'
```

Коли в `Stripped(Bold(raw))` спрацьовує `Stripped`, пробіли вже опинилися *всередині* зірочок, тож на краях прибирати нічого. Три невеликі класи дають будь-яку комбінацію без жодного підкласу на кшталт «BoldItalicStripped».

### Вправа 3

```python
import functools


def count_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        wrapper.calls += 1
        return func(*args, **kwargs)
    wrapper.calls = 0
    return wrapper


@count_calls
def greet(name: str) -> str:
    """Return a greeting."""
    return f"Hello, {name}!"


print(greet("Olena"), greet("Max"))
print(greet.__name__, greet.__doc__, greet.calls)


class Repository:
    def find(self, key: int) -> str:
        return f"record {key}"


repo = Repository()
repo.find = count_calls(repo.find)   # декорування одного об'єкта під час виконання
for key in (1, 2, 3):
    repo.find(key)
print(repo.find.calls, hasattr(Repository.find, "calls"))
```

Результат:

```text
Hello, Olena! Hello, Max!
greet Return a greeting. 2
3 False
```

З `@` декорування відбувається один раз, коли визначається `greet`, і стосується кожного виклику. Друга частина — патерн Декоратор у найчистішому вигляді: один наявний об'єкт отримує додаткову поведінку під час виконання, а клас `Repository` та інші його екземпляри лишаються недоторканими (`hasattr(Repository.find, "calls")` дорівнює `False`).
