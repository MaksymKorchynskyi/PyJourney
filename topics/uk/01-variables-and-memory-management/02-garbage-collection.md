# Збирання сміття

Python звільняє пам'ять за вас, тож викликати щось на зразок `free()` не потрібно. Більшість об'єктів знищує **підрахунок посилань** у ту мить, коли на них більше ніщо не посилається. Проте підрахунок посилань має сліпу зону: об'єкти, що посилаються один на одного по колу. Щоб знаходити й знищувати такі цикли, існує **збирач сміття** (garbage collector), а модуль `gc` дає змогу спостерігати за ним і керувати ним.

## Що ви дізнаєтесь

- Чому одного лише підрахунку посилань недостатньо, щоб звільнити циклічні посилання
- Як збирач циклів вирішує, які об'єкти є сміттям
- Як користуватися модулем `gc`: `collect()`, `disable()`, `enable()`, `isenabled()`, `get_threshold()`, `is_tracked()`
- Як безпечно спостерігати за знищенням об'єктів через `weakref` замість читання сирої пам'яті
- Що таке покоління і навіщо вони збирачеві
- Як уникати циклів і коли (зрідка) варто вимикати збирач

## Два механізми, що працюють разом

CPython, стандартний інтерпретатор, керує пам'яттю за допомогою двох механізмів:

| Механізм | Що обробляє | Коли спрацьовує |
|---|---|---|
| Підрахунок посилань | Кожен об'єкт | Негайно, щойно лічильник падає до нуля |
| Збирач циклічного сміття | Групи об'єктів, що посилаються один на одного | Періодично або під час виклику `gc.collect()` |

Майже всю роботу виконує підрахунок посилань. Він простий і передбачуваний: щойно зникає останнє посилання на об'єкт, об'єкт знищується (див. попередню тему про посилання). Збирач сміття — це запасний механізм, який займається лише тим випадком, що не під силу підрахунку посилань.

> **Зверніть увагу:** у документації Python «збирач сміття» зазвичай означає саме цей збирач *циклів*, а не керування пам'яттю загалом. Інші реалізації, як-от PyPy, використовують зовсім інший збирач, тож усе, що далі сказано про час спрацювання, стосується лише CPython.

## Проблема: циклічні посилання

**Циклічне посилання** (reference cycle) виникає, коли об'єкти посилаються один на одного напряму або через ланцюжок. Найпростіший цикл — об'єкт, що посилається сам на себе:

```python
items = []
items.append(items)   # тепер список містить сам себе

print(items)
print(items[0] is items)
```

Результат:

```text
[[...]]
True
```

Python виводить `[...]`, щоб не потрапити в нескінченну рекурсію під час відображення списку.

Реалістичніший цикл утворюють два об'єкти, які знають один про одного: батьківський і дочірній вузли, вузол і його сусід, клієнтське й серверне з'єднання.

```text
до del:                              після del first, second:

first ---> +----------+                 +----------+
           | "first"  |                 | "first"  |  лічильник 1
           +----------+                 +----------+
            |      ^                     |      ^
    partner |      | partner     partner |      | partner
            v      |                     v      |
           +----------+                 +----------+
second --> | "second" |                 | "second" |  лічильник 1
           +----------+                 +----------+

                                        жодне ім'я ззовні не вказує на пару
```

Після видалення імен лічильник кожного об'єкта все ще дорівнює 1, бо на нього посилається *інший* об'єкт. Лічильники ніколи не дійдуть до нуля, тому підрахунок посилань їх не звільнить, хоча програма вже не може дістатися жодного з цих об'єктів. Без збирача циклів ця пам'ять витекла б.

Це можна побачити за допомогою `weakref.finalize`, яка виводить повідомлення, коли об'єкт знищується:

```python
import gc
import weakref


class Node:
    def __init__(self, name):
        self.name = name
        self.partner = None


gc.disable()

first = Node("first")
second = Node("second")
first.partner = second
second.partner = first

weakref.finalize(first, print, "first destroyed")
weakref.finalize(second, print, "second destroyed")

print("deleting both names...")
del first, second
print("names are gone, but the objects are still alive")

print("running gc.collect()...")
gc.collect()
print("done")

gc.enable()
```

Результат:

```text
deleting both names...
names are gone, but the objects are still alive
running gc.collect()...
first destroyed
second destroyed
done
```

`gc.disable()` вимикає *автоматичне* збирання, щоб приклад був передбачуваним. `del` нічого не знищує. Лише `gc.collect()` знаходить цикл і звільняє обидва об'єкти. Порядок двох рядків «destroyed» не гарантовано.

Порівняйте з об'єктом, який не входить у цикл. Підрахунок посилань знищує його негайно, без допомоги збирача:

```python
import weakref


class Node:
    def __init__(self, name):
        self.name = name


first = Node("first")
weakref.finalize(first, print, "first destroyed")
print("deleting...")
del first
print("done")
```

Результат:

```text
deleting...
first destroyed
done
```

## Взаємодія зі збирачем: модуль `gc`

В оригінальній версії цього уроку використано класи `A`/`B`, наведені нижче: під час створення `A` автоматично створюється `B`, який посилається назад на `A`. Кроки такі: вимкнути автоматичне збирання, створити цикл, прибрати єдине зовнішнє посилання, переконатися, що об'єкти вижили, запустити збирач і перевірити, що їх більше немає.

```python
import gc
import sys
import weakref


class A:
    def __init__(self):
        self.b = B(self)


class B:
    def __init__(self, a):
        self.a = a


gc.disable()  # вимикаємо автоматичне збирання для цього експерименту

a = A()
a_ref = weakref.ref(a)    # слабкі посилання не тримають об'єкти «живими»
b_ref = weakref.ref(a.b)

print("refs to A:", sys.getrefcount(a) - 1)
print("refs to B:", sys.getrefcount(a.b) - 1)

a = None
print("A alive?", a_ref() is not None)
print("B alive?", b_ref() is not None)

found = gc.collect()
print("unreachable objects found:", found)
print("A alive?", a_ref() is not None)
print("B alive?", b_ref() is not None)

gc.enable()
```

Результат (Python 3.14):

```text
refs to A: 2
refs to B: 1
A alive? True
B alive? True
unreachable objects found: 2
A alive? False
B alive? False
```

Що відбувається крок за кроком:

1. На екземпляр `A` є два посилання: змінна `a` та атрибут `B.a`. На екземпляр `B` — одне: атрибут `A.b`. (Від результату `sys.getrefcount()` віднімаємо 1, щоб не враховувати її тимчасове посилання.)
2. `a = None` прибирає єдине посилання ззовні циклу. Обидва лічильники досі більші за нуль, тож обидва об'єкти виживають.
3. `gc.collect()` виявляє, що пара недосяжна, знищує її та повертає кількість знайдених недосяжних об'єктів. Точне число залежить від версії: старіші версії додатково рахують `__dict__` кожного екземпляра, тож там можна побачити більше значення.

**Слабке посилання** (weak reference, `weakref.ref(obj)`) дає змогу посилатися на об'єкт, не збільшуючи його лічильник посилань. Виклик слабкого посилання повертає об'єкт, поки той живий, і `None` після його знищення. Тому це правильний інструмент, щоб з'ясувати, чи існує ще об'єкт.

> **Зверніть увагу:** екземпляри ваших власних класів підтримують слабкі посилання. Вбудовані `list`, `dict`, `int`, `str` і `tuple` — ні: `weakref.ref([])` генерує `TypeError: cannot create weak reference to 'list' object`.

### Чому не `ctypes` і `gc.get_objects()`?

У старіших посібниках те саме перевіряють двома допоміжними функціями: одна читає лічильник посилань прямо з пам'яті через `ctypes.c_long.from_address(id(obj)).value`, інша перебирає `gc.get_objects()` у пошуках збігу за `id()`. Обидва способи ненадійні:

- Після знищення об'єкта `from_address()` читає **звільнену пам'ять**. Побачити там `0` — це везіння. Так само можна отримати сміття або аварійно завершити інтерпретатор.
- Значення `id()` використовуються повторно. Новий об'єкт може опинитися за тією самою адресою, тож «існує об'єкт із таким `id`» не доводить, що це *ваш* об'єкт.
- `gc.get_objects()` повертає лише об'єкти, які відстежує збирач. `int` чи `str` там ніколи не з'являться, навіть поки вони живі.

Для перевірки існування використовуйте `weakref.ref()` або `weakref.finalize()`, а для лічильників — `sys.getrefcount()`.

## Як збирач знаходить сміття

Збирач розглядає лише **контейнерні об'єкти**: ті, що можуть містити посилання на інші об'єкти, — списки, словники, множини та екземпляри ваших класів. Атомарні об'єкти, як-от числа й рядки, не можуть утворити цикл, тому збирач їх не відстежує. Різницю показує `gc.is_tracked()`:

```python
import gc


class Point:
    pass


print(gc.is_tracked(42))
print(gc.is_tracked("hello"))
print(gc.is_tracked(3.14))
print(gc.is_tracked([]))
print(gc.is_tracked(Point()))
```

Результат:

```text
False
False
False
True
True
```

> **Зверніть увагу:** деякі контейнери, наприклад кортежі лише з атомарними значеннями, можуть не відстежуватися задля оптимізації. Які саме об'єкти відстежуються, залежить від версії Python.

Спрощена версія алгоритму:

1. Для кожного відстежуваного об'єкта його лічильник посилань копіюється в тимчасовий лічильник.
2. За кожне посилання *від одного відстежуваного об'єкта на інший* від тимчасового лічильника цільового об'єкта віднімається 1.
3. Якщо лічильник об'єкта лишився більшим за нуль, на об'єкт є посилання **ззовні** групи (зі змінної, модуля, стека викликів тощо). Він досяжний, а разом із ним і все, на що він посилається.
4. Усі решта об'єктів — недосяжне сміття. Збирач викликає їхні фіналізатори, прибирає їхні посилання, щоб розірвати цикл, а потім їх звільняє підрахунок посилань.

Застосуймо це до прикладу з `A`/`B` після `a = None`:

```text
                 лічильник   мінус внутрішні посилання   результат
екземпляр A         1        1 - 1 (від B.a) = 0         недосяжний
екземпляр B         1        1 - 1 (від A.b) = 0         недосяжний
```

Якби `a` досі посилалася на екземпляр `A`, його лічильник дорівнював би 2, а тимчасовий лічильник — 1, і обидва об'єкти залишилися б живими: `A` — бо на нього посилаються ззовні, `B` — бо на нього посилається `A`.

## Покоління: коли спрацьовує збирач

Переглядати всі контейнери під час кожного запуску у великих програмах було б повільно. CPython спирається на спостереження: **більшість об'єктів помирає молодими**. Тимчасові списки, словники й екземпляри зазвичай зникають за кілька рядків коду, а об'єкти, що прожили певний час (конфігурація, кеші, дані рівня модуля), найчастіше живуть до кінця програми.

Тому об'єкти поділено на **покоління** (generations):

- Нові контейнерні об'єкти потрапляють у наймолодше покоління.
- Автоматичне збирання починається, коли кількість виділень пам'яті мінус кількість звільнень від попереднього запуску перевищує поріг. Молоде покоління переглядається часто.
- Об'єкти, що пережили збирання, переходять у старше покоління, яке переглядається рідше.
- `gc.collect()` без аргументів виконує **повне** збирання всіх поколінь.

```python
import gc

print(gc.isenabled())
print(gc.get_threshold())
print(gc.get_count())
```

Результат (Python 3.14.0; числа залежать від версії та програми):

```text
True
(2000, 10, 0)
(359, 0, 0)
```

`get_threshold()` повертає пороги, що запускають збирання, а `get_count()` — поточні лічильники. Пороги можна змінити через `gc.set_threshold()`, але значення за замовчуванням підходять майже будь-якій програмі.

> **Зверніть увагу:** подробиці схеми поколінь — деталь реалізації, що змінюється між випусками. Python 3.13 і старіші версії мають три покоління. Python 3.14.0 вийшов з інкрементальним збирачем, у якому пороги мали інше значення, а у 3.14.5 повернули поведінку 3.13. Ніколи не пишіть код, що залежить від того, *коли саме* відбудеться збирання.

## Фіналізатори та цикли: `__del__`

Клас може визначити метод `__del__()`, який виконується безпосередньо перед знищенням екземпляра. До Python 3.4 об'єкти з `__del__` усередині циклу неможливо було зібрати, і вони потрапляли до списку `gc.garbage`. Починаючи з Python 3.4 ([PEP 442](https://peps.python.org/pep-0442/)) збирач коректно обробляє такі об'єкти:

```python
import gc


class Connection:
    def __init__(self, name):
        self.name = name
        self.peer = None

    def __del__(self):
        print(f"__del__ called for {self.name}")


gc.disable()

client = Connection("client")
server = Connection("server")
client.peer, server.peer = server, client

del client, server
print("collecting...")
gc.collect()
print("gc.garbage:", gc.garbage)

gc.enable()
```

Результат:

```text
collecting...
__del__ called for client
__del__ called for server
gc.garbage: []
```

Два застереження лишаються в силі:

- Усередині циклу порядок виклику методів `__del__` не визначено. Фіналізатор не повинен розраховувати на те, що інші об'єкти циклу ще придатні до використання.
- Якщо об'єкт входить у цикл, його `__del__` виконається лише тоді, коли до нього дійде збирач, а це може статися значно пізніше, ніж ви очікуєте. Не закривайте в `__del__` файли чи з'єднання. Для ресурсів використовуйте інструкцію `with` (менеджери контексту).

## Як уникати циклів за допомогою слабких посилань

Найкращий цикл — той, якого ви не створили. Типове джерело циклів — зворотне посилання: дочірній вузол посилається на батьківський, працівник — на свій відділ. Зробіть зворотне посилання **слабким**, і підрахунок посилань сам усе прибере:

```python
import gc
import weakref


class TreeNode:
    def __init__(self, value, parent=None):
        self.value = value
        self.children = []
        # слабке посилання на батьківський вузол не тримає його «живим»
        self._parent = weakref.ref(parent) if parent is not None else None
        if parent is not None:
            parent.children.append(self)

    @property
    def parent(self):
        return self._parent() if self._parent is not None else None


gc.disable()  # доводимо, що підрахунку посилань достатньо

root = TreeNode("root")
child = TreeNode("child", parent=root)
weakref.finalize(root, print, "root destroyed")
weakref.finalize(child, print, "child destroyed")

print(child.parent.value)
del root, child
print("after del")

gc.enable()
```

Результат:

```text
root
root destroyed
child destroyed
after del
```

Навіть із вимкненим збирачем обидва об'єкти знищуються негайно, ще під час `del`. Батьківський вузол тримає сильні посилання на дочірні, а дочірні посилаються на нього лише слабко.

> **Порада:** один поширений цикл Python розриває за вас. Ім'я з `except SomeError as error:` видаляється наприкінці блоку `except`, бо трасування (traceback) винятку посилається на поточний фрейм, а фрейм — на `error`.

```python
try:
    1 / 0
except ZeroDivisionError as error:
    print("caught:", error)

print(error)
```

Результат:

```text
caught: division by zero
Traceback (most recent call last):
  ...
NameError: name 'error' is not defined. Did you mean: 'OSError'?
```

Якщо виняток знадобиться пізніше, присвойте його іншому імені всередині блоку.

## Вимкнення та налаштування збирача

`gc.disable()` вимикає лише **автоматичне** збирання циклів. Підрахунок посилань і далі працює, а `gc.collect()` спрацьовує, якщо викликати його самостійно. `gc.enable()` знову вмикає автоматичне збирання, а `gc.isenabled()` повідомляє поточний стан.

Обґрунтованих причин втручатися в роботу збирача небагато:

- **Вимірювання швидкодії.** `timeit` і так вимикає збирач на час вимірювання, щоб випадкове збирання не спотворило результат.
- **Ділянки, критичні до затримок.** Програма може призупинити автоматичне збирання на час короткого сплеску роботи й викликати `gc.collect()` у зручний момент.
- **Сервери, що використовують fork.** Виклик `gc.freeze()` безпосередньо перед `os.fork()` переносить усі наявні об'єкти в постійне покоління, тож дочірні процеси не чіпають їх під час збирання, і сторінки пам'яті лишаються спільними.

Якщо ви вимкнули збирач, завжди вмикайте його знову, навіть коли виникає виняток: використовуйте `try`/`finally`. І пам'ятайте: з вимкненим збирачем кожен цикл, який створює програма, стає витоком пам'яті.

### Як переглянути, що знайшов збирач

Для налагодження можна попросити збирач не звільняти недосяжні об'єкти, а зберігати їх:

```python
import gc


class Node:
    pass


gc.disable()
gc.set_debug(gc.DEBUG_SAVEALL)  # зберігати недосяжні об'єкти в gc.garbage

a = Node()
b = Node()
a.other = b
b.other = a
del a, b

gc.collect()
print([type(obj).__name__ for obj in gc.garbage])

gc.set_debug(0)
gc.garbage.clear()
gc.enable()
```

Результат:

```text
['Node', 'Node']
```

Так видно, об'єкти яких типів утворюють цикли у вашій програмі. Ще один інструмент налагодження — `gc.get_referrers(obj)`: ця функція повертає об'єкти, що посилаються на `obj`.

## Типові помилки

- **Викликати `gc.collect()` усюди, «щоб звільнити пам'ять».** Об'єкти поза циклами й так звільняє підрахунок посилань. Повне збирання переглядає всі відстежувані об'єкти і є відносно дорогим. Викликайте його, лише коли маєте на те причину.
- **Вимкнути збирач і забути ввімкнути.** Кожен цикл, створений після цього, стає витоком. Обгортайте такий код у `try`/`finally`.
- **Покладатися на `__del__` для звільнення ресурсів.** У циклі він виконується із запізненням і в невизначеному порядку, а в інших реалізаціях Python час виклику знову інший. Використовуйте `with`.
- **Перевіряти існування через `id()` або читати пам'ять через `ctypes`.** Ідентифікатори використовуються повторно, а у звільненій пам'яті може бути що завгодно. Використовуйте `weakref`.
- **Очікувати, що пам'ять процесу зменшиться одразу після збирання.** Звільнена пам'ять часто повертається у власний алокатор Python для повторного використання, а не операційній системі, тож диспетчер завдань може й не показати зменшення.
- **Бездумно створювати зворотні посилання.** Посилання на батьківський об'єкт, колбеки, що захоплюють `self`, і кеші, які зберігають об'єкти з посиланням на сам кеш, — усе це створює цикли. Якщо зворотне посилання не повинно «володіти» об'єктом, використовуйте `weakref.ref`, `weakref.WeakValueDictionary` або `weakref.WeakSet`.

## Підсумок

- CPython звільняє більшість об'єктів підрахунком посилань — одразу після зникнення останнього посилання.
- Об'єкти, що посилаються один на одного по колу, утримують лічильники один одного вище нуля, тож самий лише підрахунок посилань призвів би до витоку.
- Збирач циклічного сміття відстежує контейнерні об'єкти, знаходить групи, недосяжні ззовні, і звільняє їх.
- `gc.collect()` виконує повне збирання; `gc.disable()`/`gc.enable()` керують лише автоматичним збиранням.
- Збирання поділено на покоління, бо більшість об'єктів помирає молодими. Конкретна схема — деталь реалізації, що змінюється між версіями.
- `weakref.ref` і `weakref.finalize` дають змогу спостерігати за об'єктами, не тримаючи їх живими, а слабкі зворотні посилання допомагають уникати циклів.
- Починаючи з Python 3.4, об'єкти з `__del__` у циклах збираються, але порядок фіналізаторів не визначено. Для ресурсів використовуйте `with`.
- Не вимикайте збирач, якщо не маєте виміряної причини це робити.

## Практика

### Вправа 1: Передбачте результат

Не запускаючи код, запишіть порядок виведених рядків. Потім запустіть і перевірте.

```python
import gc
import weakref


class Box:
    pass


gc.disable()

box = Box()
box.myself = box          # об'єкт посилається сам на себе
weakref.finalize(box, print, "box destroyed")

print("step 1")
del box
print("step 2")
gc.collect()
print("step 3")

gc.enable()
```

### Вправа 2: Розірвіть цикл слабким посиланням

`Department` зберігає список своїх працівників, а кожен `Employee` — посилання на свій відділ. Якщо посилання в обидва боки сильні, утворюється цикл. Напишіть ці два класи так, щоб `Employee.department` був властивістю (property), яка спирається на слабке посилання. Потім доведіть із вимкненим збирачем, що `del` останнього імені відділу знищує його негайно, а `employee.department` після цього повертає `None`.

### Вправа 3: Виконання функції без збирача

Напишіть `run_without_gc(func, *args, **kwargs)`, яка викликає `func` з вимкненим автоматичним збиранням і повертає її результат. Вимоги:

- попередній стан відновлюється, навіть якщо `func` генерує виняток;
- якщо збирач був вимкнений ще до виклику, після виклику він лишається вимкненим.

### Вправа 4: Які об'єкти досяжні?

Три вузли утворюють кільце: `a -> b -> c -> a`. Єдине зовнішнє посилання — змінна `entry`, що вказує на `b`. Передбачте, що знищить `gc.collect()` на кожному кроці, а потім перевірте за допомогою `weakref.finalize`:

1. після `del a, b, c` (лишається тільки `entry`);
2. після `del entry`.

## Розв'язки

### Вправа 1

Результат:

```text
step 1
step 2
box destroyed
step 3
```

`box.myself = box` дає об'єкту посилання на самого себе, тому після `del box` його лічильник досі дорівнює 1, і об'єкт виживає. Автоматичне збирання вимкнено, тож цикл знаходить і знищує лише явний виклик `gc.collect()`.

### Вправа 2

```python
import gc
import weakref


class Department:
    def __init__(self, name):
        self.name = name
        self.employees = []


class Employee:
    def __init__(self, name, department):
        self.name = name
        self._department = weakref.ref(department)
        department.employees.append(self)

    @property
    def department(self):
        return self._department()


gc.disable()

it = Department("IT")
olena = Employee("Olena", it)
weakref.finalize(it, print, "department destroyed")

print(olena.department.name)
del it
print("after del it")
print(olena.department)

gc.enable()
```

Результат:

```text
IT
department destroyed
after del it
None
```

Відділ знищується ще під час `del it`, без жодного збирання, бо єдине посилання на нього від працівника — слабке. Сам працівник лишається живим, бо на нього досі посилається `olena`.

### Вправа 3

```python
import gc


def run_without_gc(func, *args, **kwargs):
    was_enabled = gc.isenabled()
    gc.disable()
    try:
        return func(*args, **kwargs)
    finally:
        if was_enabled:
            gc.enable()


def work():
    return gc.isenabled()


def broken():
    raise ValueError("boom")


print(run_without_gc(work))
print(gc.isenabled())

try:
    run_without_gc(broken)
except ValueError as error:
    print("error:", error)
print(gc.isenabled())

gc.disable()
run_without_gc(work)
print(gc.isenabled())
gc.enable()
```

Результат:

```text
False
True
error: boom
True
False
```

Блок `finally` виконується незалежно від того, чи `func` повернула результат, чи згенерувала виняток, тож стан збирача відновлюється завжди. Збереження `was_enabled` на початку не дає функції ввімкнути збирач, якщо той, хто її викликав, свідомо його вимкнув.

### Вправа 4

```python
import gc
import weakref


class Node:
    def __init__(self, name):
        self.name = name
        self.next = None


gc.disable()

a, b, c = Node("a"), Node("b"), Node("c")
a.next, b.next, c.next = b, c, a          # a -> b -> c -> a
weakref.finalize(a, print, "a destroyed")
weakref.finalize(b, print, "b destroyed")
weakref.finalize(c, print, "c destroyed")

entry = b
del a, b, c
print("collect #1")
gc.collect()

del entry
print("collect #2")
gc.collect()
print("end")

gc.enable()
```

Результат (порядок трьох рядків «destroyed» може відрізнятися):

```text
collect #1
collect #2
b destroyed
c destroyed
a destroyed
end
```

1. Перше збирання нічого не знищує. `entry` — зовнішнє посилання на `b`, тож `b` досяжний, `c` досяжний через `b.next`, а `a` — через `c.next`.
2. Після `del entry` ззовні на кільце ніщо не вказує. Лічильник кожного вузла дорівнює 1, і це посилання йде лише зсередини кільця, тому все кільце недосяжне, і друге збирання знищує всі три вузли.
